状态：**主链路契约缺口已由后续 harness-mainline 收敛，最终全量门禁通过**。见 [后续开发记录](../harness-mainline/implementation-notes.md)。

日期：2026-10-09。前置基础：[AgentLoop M1](../agent-loop-m1/README.md)。

## 目标与顺序

服务主链路：用户对话 → AgentLoop → 模型/工具 → 审批、深度研究移交或目标步骤 → 结果与可追踪记录。

严格按以下顺序开发：

1. 统一 Error / Outcome：让调用方准确知道本次操作完成、等待、移交还是失败，以及能否安全重试。
2. 统一 Event Envelope / Trace：让上述操作在持久化、恢复和订阅中使用一致的身份与因果关系。
3. 两者完成后，PolicyEngine、TaskRuntime 以这些契约为输入继续开发。Replay / Learning 后续作为消费者接入。

本轮不开发新的研究评分、Judge、回放平台或 Learning 功能，不重写深度研究内部流程。

## 开发纪律

- 一次只实施一个任务；完成本任务的验收才进入下一项。每项优先做最小纵向闭环。
- C01/C02 为规范；发现与真实代码不符时先在任务中记录具体冲突并更新契约，禁止静默偏离。
- 本轮采用适配迁移。业务状态机仍由现有服务拥有，不将数据库状态字符串机械替换成统一 Outcome。
- 新模块必须有真实调用方；禁止只定义类型、留旧路径继续自行判断，却宣称完成统一。
- 不设第二套身份体系、重试调度器、事件总线或通用插件框架。
- 完成记录只写改动、测试命令与结论、剩余问题；不另建大型验收平台。
- 每次准备提交前执行仓库根目录 `python scripts/test_all.py`，要求零失败；跳过项须列明原因。中间步骤执行有针对性的测试。
- 默认使用确定性 fake 和真实 PostgreSQL 集成测试。本轮协议改造无需付费模型评分；只有实际修改模型可见行为且存在未覆盖风险时，才按既有预算机制补最小真实 smoke。
- 不修改既有 AgentLoop M1 验收结论；其旧实现保留/删除问题单独处理，不混入本轮范围。

## 代码质量底线

小而明确的不可变类型、单向依赖、集中边界适配、显式状态转换、可检验的不变量。详细禁止事项见 C01/C02。以可读性和故障行为正确为准，不以新增抽象数量、统一命名数量或文件行数判定完成。
