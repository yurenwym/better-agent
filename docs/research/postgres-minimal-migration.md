# PostgreSQL + pgvector 最小迁移方案

> 结论：保留现有领域 Service 和 `connection.execute(...)` 调用形状，但不要用兼容层模拟 SQLite 语义。占位符应一次性机械改写；schema、UPSERT、事务竞争、序列分配、触发器、全文/向量检索必须使用 PostgreSQL 原生实现。切换后 PostgreSQL 是唯一权威数据库，SQLite 只作为只读迁移证据，不再具备运行时回切或写入路径。

## 1. 背景与问题

当前应用以 SQLite 为唯一数据库。`Database` 在构造时创建文件、执行 schema 和修复迁移；每次 `connection()` 都新建连接，`transaction()` 和 `durable_transaction()` 依赖 `BEGIN IMMEDIATE`，见 `backend/app/db.py:1140-1160`、`backend/app/db.py:1163-1339`、`backend/app/db.py:1343-1361`、`backend/app/db.py:1596-1607`。

SQL 并未封装在 repository 中，而是分散在业务 Service。静态扫描得到 38 个 `backend/app` Python 文件含 `.execute(`，共 1025 次调用；`db.py` 含 105 个 `CREATE TABLE` 文本命中（包括历史迁移中的重复定义，不能等同于 105 张现行表）。这意味着全面引入 ORM 或逐领域重写 repository 会显著扩大改动。

现有 SQLite 行为还隐含承担了并发正确性：

- `BEGIN IMMEDIATE` 把大量“读、判断、写”事务意外地串行化；PostgreSQL 默认 `READ COMMITTED` 不提供这个全库写锁。
- Turn Worker 当前先查候选再条件更新，见 `backend/app/conversation.py:1296-1349`。进程内测试已经覆盖不同 thread 并发和同 thread 串行，见 `backend/tests/test_conversation_worker.py:134-177`，但这不能证明 PostgreSQL 多连接竞争正确。
- 事件序号和多个版本号使用 `MAX(...)+1`。例如 `ThreadEventStore` 通过 thread 聚合行分配序号，见 `backend/app/events.py:99-131`；另一些聚合直接读 `MAX(seq)+1`，见 `backend/app/events.py:180-205`。
- FTS5 查询位于 `backend/app/memory_v2.py:1084-1119`；当前排序仍是 FTS/子串、pinned、importance 的组合，并非语义向量检索。
- `db.py` 包含 SQLite 的 `PRAGMA`、FTS5、`AUTOINCREMENT`、`RAISE(ABORT)` trigger 和启动期 schema recovery；业务代码另有 `INSERT OR IGNORE/REPLACE`、`datetime('now')`、`json_extract`、`GROUP_CONCAT`。

此前把“SQLite 方言”量化为 12 处不准确。以 `INSERT OR IGNORE|REPLACE`、`datetime('now')`、`PRAGMA`、FTS5、`AUTOINCREMENT`、`GROUP_CONCAT`、`json_extract`、`BEGIN IMMEDIATE`、`executescript` 等模式重新扫描，得到 **61 个原始行命中**；它包含 schema/历史迁移重复和同一语句多项特征，既不是独立语句数，也不是最终修改点数。开发前应将命中生成清单逐项归类，不能按 12 或 61 直接估算工作量。

## 2. 最小迁移边界

目标是小接口后承载数据库差异，而不是增加完整数据访问层。对业务调用方只保留三个入口：

1. `Database.connection()`：从同步连接池领取连接，提供短查询和显式 `execute/fetch*`。
2. `Database.transaction()`：从池中领取连接并提供提交/回滚边界；不承诺 SQLite 的全局写锁语义。
3. `DurableQueue`：拥有 `enqueue / claim_next / heartbeat / request_cancel / finish / fail / recover_expired` 完整状态转换，集中承载原子领取、DB clock、epoch fencing 和 PostgreSQL 锁语义。它返回不可伪造的 `LeaseToken(job_id, owner, epoch)`；业务结果写入必须通过接收该 token 的事务回调完成，不能先绕过 queue 写结果再调用 `finish`。不同 job 表通过受控队列注册表适配，绝不接受用户提供的表名或 SQL。

`durable_transaction()` 暂时作为 `transaction()` 的兼容别名，待 `plan_documents.py` 调用迁完再删除。在 PostgreSQL 中，durability 由 `synchronous_commit`、WAL、备份和部署策略决定，不能靠每个调用点临时模拟 `PRAGMA synchronous=FULL`。

建议使用当前同步技术栈：

- `psycopg 3` + `psycopg_pool.ConnectionPool`，不在迁库同时把 FastAPI 业务层全面 async 化。
- 连接使用自定义兼容 row factory，使同一 row 同时支持 `row["id"]` 与现存少量 `row[0]`；否则 `dict_row` 会破坏位置读取。新代码只允许名称读取。
- Alembic 管理 PostgreSQL schema，以手写 migration / `op.execute()` 为主，不引入 ORM 模型。部署步骤在应用启动前执行 `alembic upgrade`；应用启动**只检查**数据库 revision 与所需扩展，不自动迁移，不再执行 `SCHEMA`、`PRAGMA` 或 SQLite recovery 分支。
- Compose 增加固定大版本的 `pgvector/pgvector` PostgreSQL 服务、healthcheck 和持久卷；应用只接受 `DATABASE_URL`。正式切换构建不包含 SQLite backend 选择开关。

### 不做的改造

- 不引入 SQLAlchemy ORM、Redis、Celery、独立向量数据库或全异步数据库访问。
- 不在首期把所有 JSON TEXT 改成 JSONB、所有整数布尔改成 boolean、所有普通业务时间改成 `timestamptz`。保留为 TEXT 的时间必须统一成 UTC ISO-8601（含 `+00:00`），并由 codec/constraint/迁移校验固定格式；所有 lease/available/heartbeat 时间必须改为 `timestamptz` 并由数据库时钟计算。
- 不把 Markdown projection 变为权威数据源；仍由 PostgreSQL intent 重建。
- 不做 SQLite/PostgreSQL 双写。

## 3. SQL 方言转换策略

### 3.1 占位符必须机械改写

禁止在 connection adapter 中运行时把 `?` 替换为 `%s`。简单替换会误伤字符串、SQL 注释、JSONPath 和未来合法运算符；自己实现 SQL lexer 则把无法充分验证的解析器放进所有查询热路径。

应使用 SQL/token-aware codemod 或受控脚本对 Python SQL 字面量做一次性改写；脚本必须分辨字符串、quoted identifier、注释与 bind token，输出无法解析/含动态片段的人工审计清单。改写后人工审查 diff，并在 CI 中对生产 SQL 运行同一个 tokenizer，禁止残余 qmark bind。不能只用正则扫描作为充分证明。动态拼接 SQL 必须单独审计，标识符使用 `psycopg.sql.Identifier`，值仍参数绑定。psycopg 参数绑定采用 `%s`，不要用 Python `%` 或字符串插值。

### 3.2 必须显式原生改造的语义

| SQLite 行为 | PostgreSQL 做法 |
|---|---|
| `INSERT OR IGNORE` | 为每处声明精确 conflict target：`ON CONFLICT (business_key) DO NOTHING` |
| `INSERT OR REPLACE` | 按真实业务语义改成 `ON CONFLICT ... DO UPDATE`；不能照搬 SQLite delete-then-insert 副作用 |
| `datetime('now')`、应用时钟 lease | lease 路径统一 `clock_timestamp()`；普通审计时间可由 DB default 或现有 UTC 值写入 |
| `AUTOINCREMENT` | `GENERATED BY DEFAULT AS IDENTITY`，导入后 `setval` |
| FTS5 `MATCH` | PostgreSQL `tsvector` + GIN；中文数据必须用固定语料验收分词，必要时用 `pg_trgm` 做降级/补充 |
| `json_extract(text, path)` | 定点转成 PostgreSQL JSON 运算符或表达式 cast；首期不要求全表 JSONB 化 |
| `GROUP_CONCAT` | `string_agg`，明确顺序 |
| `RAISE(ABORT)` trigger | PL/pgSQL trigger function；完整复刻 append-only、frozen 和 scope 约束 |
| `MAX(seq)+1` | 锁聚合根行再取号，或使用独立 counter；保留既有域内顺序/唯一约束 |
| `BEGIN IMMEDIATE` | 在具体热路径使用行锁、条件写、唯一约束、`RETURNING`；必要时只对小范围事务用 `SERIALIZABLE` 并重试整个事务 |

兼容 adapter 只能保留连接、事务、row 和 cursor 的**调用形状**，不能翻译上述语义，也不能声称模拟 `BEGIN IMMEDIATE`。

## 4. Worker 领取与 fencing

### 4.1 Turn 的数据库不变量

给 `turn_jobs` 增加 `lease_epoch bigint NOT NULL DEFAULT 0`，并冗余 `thread_id NOT NULL`。生产代码只有两个 job 插入点，见 `backend/app/conversation.py:636`、`:827`，改动可控。迁移时用 `turns.thread_id` 回填并校验一致性。为避免 job 的 `thread_id` 与 turn 所属 thread 分叉，约束使用复合外键：先保证 `turns(thread_id, id)` 唯一，再建立 `FOREIGN KEY (thread_id, turn_id) REFERENCES turns(thread_id, id) ON DELETE CASCADE`。建立：

```sql
CREATE UNIQUE INDEX uq_turn_jobs_one_running_per_thread
ON turn_jobs (thread_id)
WHERE status = 'RUNNING';
```

partial unique index 是最终防线。领取协议仍要先锁 thread，避免依靠唯一冲突作为正常调度路径。

### 4.2 原子 claim 轮廓

以下 SQL 表达必要语义；实现时由 `ClaimStore` 生成固定队列 SQL，并按统一锁顺序执行：

```sql
WITH candidate_thread AS (
    SELECT t.id AS thread_id
    FROM threads t
    JOIN turns tr ON tr.thread_id = t.id
    JOIN turn_jobs j ON j.turn_id = tr.id
    WHERE (
        j.status = 'QUEUED'
        OR (j.status = 'RUNNING' AND j.lease_until <= clock_timestamp())
    )
      AND NOT EXISTS (
          SELECT 1 FROM turn_jobs active
          WHERE active.thread_id = t.id
            AND active.status = 'RUNNING'
            AND active.lease_until > clock_timestamp()
      )
    -- 过期 RUNNING 必须先接管，避免已有半成品被后续 QUEUED turn 越过。
    ORDER BY CASE WHEN j.status = 'RUNNING' THEN 0 ELSE 1 END,
             j.started_at, tr.created_at, tr.id
    FOR UPDATE OF t SKIP LOCKED
    LIMIT 1
), candidate_job AS (
    SELECT j.turn_id
    FROM turn_jobs j
    JOIN turns tr ON tr.id = j.turn_id
    JOIN candidate_thread ct ON ct.thread_id = j.thread_id
    WHERE j.status = 'QUEUED'
       OR (j.status = 'RUNNING' AND j.lease_until <= clock_timestamp())
    ORDER BY CASE WHEN j.status = 'RUNNING' THEN 0 ELSE 1 END,
             j.started_at, tr.created_at, tr.id
    FOR UPDATE OF j SKIP LOCKED
    LIMIT 1
)
UPDATE turn_jobs j
SET status = 'RUNNING',
    lease_owner = %(owner)s,
    lease_epoch = j.lease_epoch + 1,
    lease_until = clock_timestamp() + %(lease)s::interval,
    attempts = j.attempts + 1,
    started_at = COALESCE(j.started_at, clock_timestamp())
FROM candidate_job c
WHERE j.turn_id = c.turn_id
RETURNING j.turn_id, j.thread_id, j.lease_epoch, j.lease_until, j.attempts;
```

所有 enqueue/claim/续租/取消/失败恢复/最终写入只能经过 `DurableQueue`。claim 与 `recover_expired` 优先接管过期 RUNNING，再领取同 thread 后续 QUEUED，避免旧 turn 的半成品和顺序被越过。所有 lease 判断使用数据库时钟。worker 持有 `(lease_owner, lease_epoch)` token；heartbeat、checkpoint、message delta、状态转换和 finalize 都必须包含：

```sql
WHERE id = %(id)s
  AND status = 'RUNNING'
  AND lease_owner = %(owner)s
  AND lease_epoch = %(epoch)s
  AND lease_until > clock_timestamp()
```

并严格要求 `rowcount = 1`。否则抛出 lease lost，禁止旧 worker 写入任何业务结果。最终提交不能只 fence job 状态，而让 message/event/result 绕过检查；fence 检查和结果写入必须在同一事务。

切换前要把该完整状态机协议覆盖到所有 durable worker，而非只修 Turn：至少包括 `turn_jobs`、`agent_tasks`、`research_jobs`、`memory_archive_jobs`、`goal_daily_reviews`、`evaluation_runs`、conversation archive state，以及实际带 lease/接管语义的 direction projection / tool execution claim。`agent_tasks` 和 `memory_archive_jobs` 已有 epoch；其他表应补齐。先做 inventory 测试，任何含 `lease_owner/lease_until` 却无 epoch、任何业务代码直接改变 queue 状态、或 finalize 未 fence 的路径都阻止发布。

## 5. pgvector 与记忆召回

PostgreSQL 中新增固定维度的 revision 向量，而不是给可变 entry 直接挂向量：

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE memory_embeddings (
    revision_id text NOT NULL REFERENCES memory_revisions(id) ON DELETE CASCADE,
    model_id text NOT NULL,
    model_version text NOT NULL,
    dimensions integer NOT NULL,
    content_hash text NOT NULL,
    embedding vector(<固定维度>) NOT NULL,
    created_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    PRIMARY KEY (revision_id, model_id, model_version)
);

CREATE INDEX memory_embeddings_cosine_hnsw
ON memory_embeddings USING hnsw (embedding vector_cosine_ops);
```

`memory_embedding_jobs` 作为 transactional outbox。创建 `memory_revisions`、更新 `memory_entries.current_revision_id`、写 evidence、插入 embedding job 必须在**同一 PostgreSQL 事务**；绝不在该事务中调用外部 embedding API。job 以 `(revision_id, model_id, model_version, content_hash)` 幂等，worker 成功后验证 revision hash 和固定维度再 upsert 向量。

召回采用语义优先级联：

1. SQL 中先硬过滤 `owner_id`、project/scope、ACTIVE/current revision；pinned 约束按现有规则保留。
2. query embedding 成功且版本匹配时用 pgvector cosine Top-K。
3. embedding 超时/失败、索引未就绪、达标候选不足时降级 PostgreSQL FTS；路径、错误码、版本号等精确标识主动补充 FTS。
4. 去重、importance/recency 排序并按 token budget 裁剪；context pin 仍冻结 revision ID 和渲染 hash。

先用 exact vector search 建立标注集基线，再启用 HNSW。pgvector 官方说明 approximate index 的过滤通常在索引扫描后发生，因此 owner/project 过滤可能导致候选不足；需要验证 iterative scan、提高 `ef_search` 或按规模采用 partial/partition 策略，不能在应用层后过滤租户。

## 6. 一次性迁移、切换与恢复

### 6.1 准备与影子验证

1. Alembic 从空库创建完整 PostgreSQL schema、约束、trigger 和扩展。
2. 写独立 SQLite -> PostgreSQL 离线迁移命令。读取 SQLite 一致性快照，按 FK 拓扑批量 `COPY`；对 identity 列保留原值并在导入后重置 sequence。
3. 每次迁移生成 manifest：源 SQLite hash、schema revision、每表 row count、主键集合 hash、规范化逐行 hash、NULL/空串/JSON/Unicode 统计、外键孤儿、序列水位。
4. 从 PostgreSQL 重建 Markdown projection、FTS 和 embedding jobs；Markdown 是验证产物，不参与数据迁移回写。
5. 在 PostgreSQL 环境运行完整 Service/API 和真实多连接并发测试。可做 SQLite 只读 shadow 比较，但不得双写或把 PG shadow 结果返回用户。

### 6.2 切换窗口

1. API 进入 maintenance/read-only，停止 scheduler 和全部 worker；等待在途任务安全结束或明确让 lease 失效。
2. 对 SQLite 做最终 checkpoint/backup 并记录停写水位；重新全量导入或执行经验证的最终增量。
3. manifest、FK、约束、事件序号、memory revision/current pointer、context pin hash 全部通过才允许启动。
4. 启动只包含 PostgreSQL 配置的单实例，跑 smoke；再逐步放开 worker 并发。
5. SQLite 文件转只读归档并从应用运行账号撤销写权限。

### 6.3 回滚原则

在 PostgreSQL 接受第一笔新写入之前，可以保持停写并切回最终 SQLite 快照。**一旦 PostgreSQL 接受新写，禁止切回 SQLite**，否则会丢失新 thread、turn、memory revision、审批和审计事件，也无法可靠合并两套事件序列。

切换后的故障处置只有三类：

- 应用回滚：部署仍兼容当前 PostgreSQL schema 的前一应用版本。
- 前向修复：修复代码/schema，PostgreSQL 继续作为权威源。
- 数据库恢复：从 PostgreSQL base backup + WAL/PITR 恢复到新实例；按明确 RPO 接受时间窗数据损失。

首期 schema 采用 expand/contract，至少跨一个稳定发布再删除旧列/约束，确保应用可回滚但数据库权威源不回退。

## 7. 分阶段开发顺序

### 阶段 A：固定契约

- 引入 psycopg pool、兼容 row、三个入口和 Alembic 空库 schema；部署负责 upgrade，启动仅 check revision。
- 完成占位符 codemod 与 SQLite 方言清单；逐项原生改写，CI 禁止回归。
- 保持现有 Service/API 签名不变。

门禁：全部 PostgreSQL contract test 通过；应用启动不执行 SQLite schema/recovery。

### 阶段 B：并发正确性

- 给所有 durable queue 加 `lease_epoch`、DB clock 和 finalize fencing。
- Turn job 冗余 `thread_id`、partial unique index，并用原子 claim。
- 修复所有 `MAX(seq)+1`、CAS/upsert、append-only/frozen trigger。

门禁：真实多连接/多进程竞争、接管、旧 epoch 迟到写、死锁测试通过。

### 阶段 C：记忆检索

- 建 embedding outbox、worker、vector 表、exact search、FTS fallback 和 trace 指标。
- 标注集达标后创建/启用 HNSW；embedding 未就绪不阻塞记忆保存和回答。

门禁：scope 隔离为零泄漏；语义、精确词、降级、模型换版和 stale vector 用例通过。

### 阶段 D：迁移与唯一权威源切换

- 完成离线迁移/manifest、只读 shadow、备份恢复演练和停写 runbook。
- 一次性切换 `DATABASE_URL`，移除生产 SQLite 写路径。

门禁：下一节所有验收用例通过，且明确签署“PG 新写后不回切 SQLite”。

## 8. 验收用例

| ID | 场景 | 通过标准 |

| A1 | 两个不同 thread 同时提问 | 两个 turn 同时 RUNNING 且都正常流式完成；并发不超过配置上限 |

## 9. 测试用例与发布门禁

### 单元/静态测试

- row adapter：名称/位置读取、`rowcount`、NULL、整数布尔、JSON text、UTC 值、rollback。
- SQL lint：使用与 codemod 相同的 SQL tokenizer 证明生产 SQL 无残余 qmark bind、`INSERT OR ...`、`PRAGMA`、FTS5、SQLite time/JSON 函数；另以简单正则作快速提示，但不以它替代 token 解析。动态标识符必须使用安全 composition。
- 每处 `ON CONFLICT` 有明确业务约束；相同幂等键同 payload 重放，不同 payload 报冲突。
- queue registry：所有含 lease 的表都声明 epoch、DB clock、heartbeat/finalize fence；业务模块不得直接 UPDATE queue status/lease 字段。
- ranking：pinned、semantic 阈值、精确标识补充、lexical fallback、稳定 tie-break 和 token budget。

### PostgreSQL 集成测试

- 将现有 `backend/tests` 按领域迁到真实 PostgreSQL fixture；SQLite suite 只能作为历史行为参考，不能作为发布凭据。
- 使用独立 connection/进程同时 claim 同 job、同 thread 两 job、不同 thread 两 job；分别断言 1、1、2 个成功。
- 新 epoch 接管后，旧 epoch 尝试 heartbeat、checkpoint、message delta、event、result/finalize，全部更新 0 行。
- 在 claim、结果写入、revision/outbox、vector upsert、projection intent 各事务边界注入崩溃，验证全有或全无/可重试。
- 对 append-only/frozen 表执行 UPDATE/DELETE，确认 PostgreSQL trigger/权限拒绝。
- 1000 轮并发竞争；出现 deadlock/serialization failure 时只允许重试完整幂等事务，并监控重试率。

### 迁移与端到端测试

- golden SQLite fixture 覆盖 Unicode、长 Markdown、大 JSON、NULL/空串、删除态、过期 lease、失败/待恢复 projection intent。
- 导入中断后重跑不产生重复；identity sequence 在最大旧值后继续。
- 全流程：create thread -> concurrent turns -> SSE reconnect -> Ask continuation -> memory proposal/accept -> next-turn recall -> delete/invalidate pin。
- 多 owner 同时写相似内容，API、FTS、pgvector、episode、evidence、projection 全链路零泄漏。
- 从 PostgreSQL 备份恢复到隔离实例后运行同一 smoke，而非只检查 `pg_restore` 退出码。

### 建议量化门禁

- 数据迁移 row count、PK set、canonical row hash、FK、关键领域不变量：100% 通过。
- 同 thread 重叠、旧 epoch 有效写、跨 owner/project 泄漏、重复有效终态：均为 0。
- HNSW 对 exact Top-10 的 `Recall@10 >= 0.95`；ACTIVE current revision 的 READY 覆盖率达到 99% 后才默认开启 semantic。
- embedding 查询设置短超时并记录 `embedding_ms/vector_search_ms/keyword_search_ms/retrieval_mode/fallback_reason`；超时不得拖垮模型 TTFT。
- 连接池等待、claim p95/p99、锁等待、deadlock、serialization retry、embedding backlog 和 lexical fallback rate 都进入轨迹/监控。

## 10. 主要风险

1. **隐藏竞争条件**：SQLite 全局写锁曾掩盖 read-modify-write 竞态。必须围绕聚合根、queue、seq、CAS 做原生事务审计。
2. **伪兼容层**：运行时改 SQL 看似减少 diff，实际让错误跨 1025 个调用点扩散。兼容只保留调用形状。
3. **时间类型漂移**：psycopg 可返回 `datetime`，现有代码常按 ISO string 处理。首期明确列级 codec；普通 TEXT 时间严格为 UTC ISO，lease 内聚在 `DurableQueue` 并使用 DB clock。
4. **trigger/约束遗漏**：append-only、frozen、scope trigger 若漏迁，会形成静默数据破坏。
5. **中文 FTS 退化**：PostgreSQL 默认配置不保证等价于 FTS5 trigram，必须以项目真实中文语料验收。
6. **过滤后的 ANN 候选不足**：HNSW 过滤和多租户 scope 组合可能漏召回；必须 exact 对照并启用合理扫描策略。
7. **embedding 一致性**：revision 和 job 不同事务会出现永久缺向量；混用模型版本/维度会产生无意义距离。
8. **错误回滚预期**：PG 新写后回切 SQLite 必然分叉。运维 runbook 必须把应用回滚、前向修复、PG PITR 与 SQLite 回切明确区分。
9. **测试环境失真**：只跑 SQLite 或单 asyncio 连接无法验证 PostgreSQL 锁与连接池，CI 必须启动真实 pgvector PostgreSQL。

## 11. 官方依据

- [psycopg 连接池](https://www.psycopg.org/psycopg3/docs/advanced/pool.html)：同步 `ConnectionPool` 支持多线程领取连接，连接不足时请求排队；pool 是独立安装包。
- [psycopg row factories](https://www.psycopg.org/psycopg3/docs/api/rows.html)：默认 tuple row 与 `dict_row` 的返回契约不同，因此本项目需要显式兼容 row 或机械改完位置读取。
- [psycopg 参数绑定](https://www.psycopg.org/psycopg3/docs/basic/params.html)：值使用 `%s` 参数绑定，不使用 Python 字符串拼接。
- [PostgreSQL SELECT locking](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)：`SKIP LOCKED` 适用于多个消费者访问 queue-like table，但会产生不一致视图，不适合普通查询。
- [PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)：默认 `READ COMMITTED`，复杂读写谓词不能假定获得 SQLite 式全局写串行化。
- [PostgreSQL partial index](https://www.postgresql.org/docs/current/indexes-partial.html)：可只约束满足谓词的行，适合表达每 thread 仅一个 RUNNING job。
- [PostgreSQL ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT)：为幂等插入/更新提供原子冲突处理。
- [Alembic migration environment](https://alembic.sqlalchemy.org/en/latest/tutorial.html#the-migration-environment)：migration environment 随应用源码维护，`env.py` 可自定义连接和事务执行。
- [pgvector 官方 README](https://github.com/pgvector/pgvector)：支持 exact/approximate search、cosine、HNSW、过滤与 iterative scan，并说明 approximate index 的速度/召回权衡。
- [PostgreSQL WAL/PITR](https://www.postgresql.org/docs/current/continuous-archiving.html)：base backup 与持续 WAL 归档共同支持时间点恢复。

## 12. 最终建议

批准 PostgreSQL + pgvector 作为目标架构，但按 A-D 四个可验证阶段交付。这里的“修改幅度最小”是保留现有 Service/API 和大部分 CRUD 调用形状，不是用字符串翻译掩盖数据库语义差异。真正必须集中重写的只有 schema/migration、所有并发 claim/fencing、序号/CAS/upsert、trigger、FTS/向量检索和一次性迁移工具；这些路径少改任何一类，都会让“唯一权威数据库”和多 worker 并发只停留在配置层面。
