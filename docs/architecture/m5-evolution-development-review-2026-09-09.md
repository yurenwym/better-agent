# Better Agent 自进化优化开发方案与评审

版本：v2，2026-09-09。状态：设计评审通过，三票赞成、零票反对、零票弃权；尚未实施。

本文是设计与开发计划，不代表已实现、已验收或获得付费评测、Canary、发布授权。M1–M4 历史验收维持原记录；本轮仅检查源码和编写文档，没有启动应用模型或修改数据库。外部资料服务不可用，以下结论以本地实现为依据。

## 1. 结论与适用范围

采用“自动记问题 → 人工选择问题 → 有预算地提出角色级候选 → 离线淘汰 → 经批准的配对评测 → 经批准的灰度 → 人工晋升”。个人使用场景流量低，允许长期保持建议状态；没有足够证据就不发布。

M5 改善可复现的行为错误：回答约束遗漏、计划条件遗漏、研究结论超过证据、协作结果未保留分歧。个人偏好和事实仍由 M1 记忆负责。代码错误、402、认证、来源不可达、数据库故障和输出协议错误进入工程/运维问题单，不自动归因为提示词不足。M4 的引用恢复和截断问题应作为工程负例，不应拿来证明提示词自进化有效。

第一版仅优化一个明确角色的一个允许提示词片段。暂不自动修改代码、工具权限、长期记忆、预算、发布门禁、模型路由或整个提示词树。复用 PostgreSQL、现有预算、不可变 bundle、候选状态机和配对评测，不新增训练平台或第二数据库。

## 3. 开发顺序与出口

### P0-A：先分离观察和付费生成

修改 startup.py、experience_observer.py、evolution.py 及相应 API。默认 observer 只做本地投影；候选生成必须有显式批次、owner、根预算、调用数/费用/时限、停止状态。授权变量不能代替授权记录。首错停止且同批不得后台再次发起请求，重启继续保留停止状态。幂等键由问题指纹、基线版本与生成配置共同决定；重复点击不重复扣费。

将 observer offsets 改为真实事件游标，按流分批扫描，投影和游标在同事务提交。记录可查看的错误和最后成功进度，避免静默失败。未被授权的后台任务不得附带调用候选 proposer 或 Canary judge；其他产品安全审查必须有独立目的和预算。

出口：模拟三条重复失败也不产生模型调用；生成失败后多次 tick/重启仍无额外调用；重复批次请求幂等；零预算网络前拒绝；增量投影与重启不漏事件。

### P0-B：建立可信问题与证据记录

补全 PARTIAL、失败、取消和用户纠正；执行 completed 只代表流程结束，不直接等于质量正确。优先从实际 run/turn/job 获取 bundle、角色、调用 ID、错误类别、finish_reason、root_budget_id、来源版本和证据引用。缺失标 UNKNOWN，不回填当前 stable。

独立样本按根任务和重试关系归组。一个根任务的 turn、research、expert 事件是同一谱系；正常后续独立任务不能全部并入同一 thread。保留失败→重试→完成的顺序，归并不删除原事件。测试/验收/合成来源有显式 provenance，默认不进入真实 DISCOVERY 计数。

复用 experience evidence_json，必要时添加可索引 root/角色/provenance/version 字段。默认只记录脱敏元数据。正文及可还原正文的片段回放必须单独显式授权，绑定主体、源范围、用途、有效期；生成批次批准不等于正文授权。授权后仍仅使用最小必要片段和引用，每次读取校验 owner、授权及源状态。授权撤销、过期或源删除后立即禁止后续读取，关联候选/回放/评测资格失效，禁止从快照或审计重建正文。HOLDOUT 和 SAFETY 正文、答案及逐题诊断不提供给 proposer；仅保留无正文审计摘要。

额外验收：未授权、撤销、到期三种情形均在读取正文及网络调用前拒绝。模型请求已发出而落库前崩溃时记录 UNKNOWN/待人工核对，重启不能因没有候选结果而重发。

出口：PARTIAL可见；402不能触发行为候选；同根多层/重试只计一次；跨owner不可读；删源后不可生成、评测或发布；旧版本证据不被当前版本覆盖。

### P0-C：有限的角色级候选

保留“三个独立 DISCOVERY 谱系”为提出建议的最低线，不能当统计结论。候选包含问题指纹、原始证据引用、根因假设及置信限制、target_role、allowed_path、base_bundle、patch、预期指标、风险与回放案例。

模型只提出文本片段，代码负责允许路径校验和合并。第一版只支持 researcher 的证据表述片段，后续逐角色扩展。深层 diff 发现权限、工具、预算、路由、发布规则或其他角色变化立即拒绝。相同问题与基线最多一个活动候选；失败候选保留，只有新证据/新基线或用户显式重新提案才创建新版本。

首个目标具体为 backend/app/research/live.py 的 LiveResearchModel.write 深度研究章节写作提示词，role=researcher、purpose=write_research_section；不是多Agent专家中的researcher，也不覆盖plan/distill/audit其他阶段。

出口：越界patch拒绝；候选无法修改评测门槛；proposer看不到留出；相同输入幂等；来源撤销使候选资格失效。

### P0-D：先证明候选被执行，再证明它有用

为现有 paired evaluator 增加真实角色回放适配，调用与生产一致的提示词构造入口。两臂同模型/输入/来源快照/上下文，仅改变允许片段；记录实际 system prompt digest、bundle、角色、模型配置、输出/成本摘要。先用无网络 spy 验证两臂确实只在目标片段不同，禁止“换bundle标签但提示词不变”。

原故障与邻近场景成为版本化 DEV 专题集，用于便宜淘汰；最有希望的一个候选才提交完整发布评测审批。现有60例套件保留原版本，不原地换题；新增专题 HOLDOUT 必须在候选生成前冻结，并按谱系划分。不得复用留出逐题失败指导同一候选后再把该留出宣称独立。

所有可发布 prompt/policy 都必须通过同一版本化 release contract；旧两题结果仅作为冒烟、不可进入批准或灰度。评测结果分为通过、失败、证据不足：同分不证明质量改善。冻结正的最小实际增益及置信区间规则，具体数值在基线分析后、见候选留出结果前确定。成本/延迟目标另用质量非劣界限与安全零回退，不强求质量赢20题；这一规则是新评测版本，不能回写旧结果。

裁判不同profile ID不等于独立模型：记录实际模型配置/家族，配合匿名顺序、确定性断言和少量人工校准。样本不足或裁判分歧过大记证据不足。三轮成功不能代替统计门槛。

出口：两臂真实prompt命中测试；旧评测拒绝发布；目标无改善拒绝；任一关键安全退化拒绝；留出泄漏拒绝；费用未知不按0；保存失败报告后才能精确清理测试数据。最终报告、摘要和同一批次退出码必须一致。

### P1：复用受控灰度与回滚

审批绑定候选/报告/权限/目标bundle摘要，并新增发布契约版本、来源有效性、灰度预算与截止时间。任何绑定改变均重新审批。灰度只对明确匹配的目标角色任务分流，任务开始即固定版本；按实际角色prompt命中计样本，不以无关成功对话凑数。

保留现有最低20 challenger和20 champion样本要求，生产不能通过参数降低；它是最低数量，不是收益充分条件。低流量场景到期不足就停止并标证据不足。晋升还检查预冻结目标增益、成本、质量非劣、安全及实际prompt命中。全量晋升必须新的人工决定。

经单独批准的灰度策略定义安全失败、成本超限、错误率恶化等回滚条件；安全待判先禁止晋升。审批过期后停止新challenger分配，证据撤销即冻结发布资格。在途任务按原bundle完成，后续任务恢复stable；回滚只改指针、不覆盖历史。并发发布须比较当前stable/部署版本，不能覆盖别人的后续合法变更。

出口：灰度真实角色命中；不足样本不晋升；无安全结果不晋升；超预算停止；审批失效；自动回滚、并发发布与重启恢复。调用与费用上限需独立审批，不在本设计中推算供应商价格。

## 4. 数据、迁移、文件与测试边界

| 范围 | 主要文件 | 数据处理 |
| --- | --- | --- |
| 观察与生成分离 | startup.py、main.py、experience_observer.py | offsets与生成批次/根预算关联 |
| 事实和候选 | evolution.py、api.py | experiences/candidates增量字段或版本化JSON |
| 真实回放与发布契约 | real_evaluation.py、model_control.py、各角色提示词入口 | 不可变suite、report、实际prompt摘要 |
| 灰度与展示 | evolution.py、成长页面/候选卡片 | 曝光、审批、发布策略版本与可解释状态 |

实施时先列全字段、CHECK、终态消费者和迁移SQL，再用 Alembic 增量迁移。只使用当前 better_agent；禁止测试fixture自动创建隔离数据库或容器。所有测试owner/job/bundle按批次精确登记，清理前导出脱敏证据，清理事务失败必须可见，最后验证残留与stable。离线测试用mock/内存对象，不发模型请求。禁止整套测试不加筛选地触发旧隔离库fixture。

不删除旧候选、评测或审批历史；旧报告缺新字段即不可发布。数据库回滚优先停用新行为和兼容读取，不做破坏性schema降级。

## 5. 验收节奏与成本控制

先完成P0全部离线门禁，再申请一个明确目的的真实评测批次。DEV、完整发布评测、Canary分别冻结目的与预算；每次新付费批次单独批准，零fallback、零网络重试、首错停止。失败保留输入版本/阶段/错误/finish_reason/费用及清理证据，不不断扩大批次寻找成功。

针对单个提示词优化，不运行无关M1–M4全量付费验收。只有影响对应能力的源码或新失败出现才扩大回归。M5出口是一个真实故障专题的改善证据、邻近能力无退化、发布资格不可绕过，以及单独批准的灰度/回滚证据；若统计收益不足，交付“无发布候选”也是有效研究结果，不能标已改善。

## 6. 独立投票规则与记录

三位评审分别为架构、评测发布、收益成本。对同一冻结版本方案独立投赞成/反对/弃权，列理由和未解决阻断项；不能为达到通过而更换投票者。至少2/3赞成且没有未解决的权限、数据、安全或评测真实性硬阻断，设计评审才通过。有阻断则修订明确版本后重新投票并保留前轮。

这是同一模型体系内不同评审上下文的工程意见，不代表三个独立实验或用户授权。设计投票通过不自动授权实现、付费、Canary或晋升。
