# Better Agent 可靠性完善开发方案

日期：2026-09-08

状态：grilling 三轮、Q1–Q14 的推荐方案均已获用户确认，用户已批准实施。M0/M1进行中，见docs/acceptance/m1-memory-development.md。本文不批准任何进化候选、Canary 或付费测试批次。

## 1. 目标与非目标

按“记忆系统 → 对话与上下文 → 多 Agent → 深度研究 → 自进化”顺序，将当前可运行的本地单用户系统完善为有质量证据、有失败边界、可恢复的工作流。保留 PostgreSQL 为唯一运行时权威数据源，Markdown 为可重建投影。

不新增多租户认证平台、分布式队列、向量数据库、无限递归 Agent 或自动代码进化。当前已有隔离、版本、审批、快照和评测机制优先复用，不为同一事实创建第二套权威存储。

之前的211项测试通过和人工介入后的流程成功是历史基线，不证明新目标已达成，也不证明无人干预成功率。既有验收模拟数据不计入真实用户偏好或独立进化证据。

## 2. 已确认的决策

| 决策 | 确认结果 |
| --- | --- |
| Q1 产品范围 | 本地单用户可靠版；保留作用域隔离，不扩大为多人生产平台。 |
| Q2 归档失败 | 允许明确标记上下文不完整的受限普通回答；依赖缺失历史的写入、计划修改和执行继续阻断。 |
| Q3 优先级 | 事实正确、状态一致优先；时间、调用数和费用有界；覆盖不足须坦诚说明。 |
| Q4 发布权限 | 自动观察、生成、评测；人工批准后灰度；安全或退化阈值触发自动回滚，不自动全量晋升。 |
| Q5 记忆变更 | 摘要可自动生成；长期记忆由明确请求或批准提案写入；冲突不静默覆盖。 |
| Q6 目标变更 | 更新对话任务状态；文档和执行日程先出差异预览，确认后更新；不改写已完成历史。 |
| Q7 协作触发 | 默认单Agent，按独立子问题选最多3个专家；显式协作请求遵从；部分成功明确展示。 |
| Q8 研究不足 | 交付有依据的部分并标注缺口；必需来源不可用不得换源冒充；关键无据结论不得进入执行建议。 |
| Q9 运行预算 | 单任务共享时间、调用、费用硬上限；阶段、重试、备用模型不重置预算；备用模型须预授权。 |
| Q10 进化数据 | 默认脱敏元数据；正文回放单独授权；同源重试去重；模拟数据隔离；零增益不晋升。 |
| Q11 数据升级 | 备份后增量迁移；保留原文；派生物按需重建；旧候选重新评测，不篡改历史结论。 |
| Q12 完成标准 | 回归、安全、一致性检查全通过；固定案例对比；核心真实流程连续3次无人工修补通过。 |
| Q13 测试费用 | 离线优先；真实测试批次事先批准调用上限、费用预计和硬上限；无法可靠计价不自动启动。 |
| Q14 交付方式 | 五阶段顺序交付；当前阶段通过后推进下一阶段；跨模块只做当前阶段必要前置改动。 |

## 3. 执行与共同门槛

M0是开发准备，不是第六个功能阶段：确认工作树基线，保留现有未提交修改，登记代码版本与迁移版本；在获准实施后执行数据库备份并在隔离库验证恢复。不得通过回退用户修改获得干净工作树。

每阶段按同一顺序执行：冻结该阶段案例和指标 → 离线复现 → 最小实现 → 单元/API/PostgreSQL/必要UI回归 → 审批真实测试批次 → 固定条件下对比 → 连续3次核心流程验收 → 阶段交付。

- 所有预期成功、拒绝、部分完成、取消和恢复路径按各自契约判定；部分交付不冒充完整成功。
- 安全越权、丢数据、错误版本写入、取消后非法提交、超预算追加调用均为硬失败，不以平均分抵消。
- 质量案例、费用口径和性能阈值在候选评测前冻结。故障修复后保留失败记录，重新开始连续3次验证，不挑选成功样本。
- 性能先取基线：记录排队、上下文、归档、首token、生成和总时长，以及重试数、模型调用数和费用。样本不足时不报告可靠P95，不把缺失费用计为0。
- 使用已有测试工具、数据库连接、幂等和租约；任何新增状态要同步覆盖API、事件、worker恢复、前端展示和过滤逻辑。

真实模型每批测试单必须包括：代码/模型/提示词/数据集版本、案例数量、基线与候选重复次数、各角色单次输入输出上限、总调用上限、最长持续时间、最坏费用及停止条件。价格与计价语义执行前核验。需要正文材料或新备用模型时分别取得授权。

## 4. M1 记忆系统

目标：提高相关记忆命中和事实保真，避免无关信息注入；不以丢历史换取表面可用性。

实现顺序：

1. 在MemoryContextProvider过滤无关候选，再排序。显式置顶内容仍受作用域、有效期、删除状态和预算限制；非置顶内容必须达到冻结的相关性门槛。
2. 同时使用语义与关键词候选，去重合并；未向量化条目仍可关键词召回，避免因部分嵌入缺失关闭所有语义结果。阈值和融合权重通过案例校准，不预设“越多越好”。
3. 渲染Episode的归因摘要、决策、未决事项，保留来源版本；不得把助手建议渲染为用户确认事实。当前显式输入与旧记忆冲突时仅覆盖本次任务条件，长期变更仍需授权。
4. 调整归档触发时机，在接近热历史预算前后台处理；复用现有队列和fencing，保留死信与有界重试，增加可见恢复入口。
5. 引入明确的上下文完整性标记。归档未完成时，仅允许与缺失历史无关的普通只读回答；“继续之前”“修改计划”等依赖无法确定时保守阻断。禁止伪造摘要或推进未提交覆盖游标。

主要文件：backend/app/memory_v2.py、memory_archive.py、transcript.py、conversation.py，以及对应记忆/对话页面与测试。

复用：context pin的owner/thread/project/query/预算绑定、版本校验、删除失效与原子轮次打包。Episode渲染改动必须升级renderer版本；旧pin不得按新格式解释。

验收：相关/无关记忆对照、同义召回、部分嵌入缺失、用户纠正、过期/删除/归档、跨项目隔离、摘要遗漏与归因、归档失败受限回答、依赖写入阻断、恢复后无丢失或重复。

交付：记忆选择与排除证据、版本化上下文渲染、归档恢复契约、质量基线与回归报告。

## 5. M2 对话与上下文

依赖：M1提供可信的相关记忆、结构化Episode和上下文完整性标记。

1. 从已确认询问、用户明确约束、当前计划和行动构建版本化任务状态：当前目标、约束、未决问题及来源引用。业务对象继续是权威，状态只保存必要引用和已确认字段，不复制一套计划数据库。
2. 目标改变后标记旧计划可能过时，区分“对话目标更新”“计划文档修订”“执行调整”。后两者必须有差异与版本确认，取消或拒绝不改变旧状态。
3. 固定打包优先级：安全约束和当前请求必留；已确认任务条件、当前目标/计划按依赖保留；近期完整轮次和相关记忆有界装入。必需块放不下时明确失败，不把必要条件悄悄丢弃。
4. 统一运行版本：所有模型角色从所属turn/job/run的不可变bundle读策略；重试和恢复继续使用同一绑定。不得用动态stable回调覆盖运行中版本。记录实际应用的prompt digest。
5. 复用ModelGateway/ModelCallContext统一各角色生成预算和错误分类。余额不足、认证、限流、网络、截断、结构错误、上下文超限分别处理；有限重试，不把永久失败降级为业务质量错误。
6. 合并重复意图识别，显式UI动作走确定路径；歧义才澄清。整条根任务建立共享预算账本，包含辅助判定、专家、修复和备用调用，后续阶段复用。

主要文件：backend/app/conversation.py、live_model.py、token_budget.py、model_gateway.py、model_control.py、startup.py、plan_context.py、goal_context.py。

验收：目标变更不静默改计划、ask续接、最新约束优先、长历史压缩、完整工具组、上下文不足受限输出、重启重放、并发预算预留不超额、版本切换不影响在途任务、各角色实际prompt与分配bundle一致。

交付：上下文装配契约、任务状态差异、统一预算与错误契约、时延与调用数对比。此阶段验证bundle绑定，但不执行候选发布。

## 6. M3 多 Agent

依赖：M2的任务状态、运行版本和共享预算；M1的有界相关上下文。

1. 复用agent_context_snapshots，自动构造带来源版本的会话、研究、计划上下文。用户不再手工粘贴整篇报告；快照不能包含无关记忆或可执行的不可信指令。
2. 明确角色合同：researcher核验证据与缺口；planner核查时间、依赖和可执行性；critic寻找反例、约束违反和风险。避免复制同一objective仅换角色名称。
3. 默认单Agent；按任务需要选择专家，最多3个；只有当前材料不足以安全协作时才询问。相同模型的不同角色不计为独立外部证据。
4. 协调器引用产物、保留分歧和未决事项。完整成功与部分成功有显式机器可读标记，前端、API、观察器一致解释，不能让外层SUCCEEDED掩盖缺少必需专家。
5. 超时、重试、结构修复均计入根预算；只重试失败且可重试的子任务，保留已成功产物及版本。取消传播后禁止后到结果覆盖终态。

主要文件：backend/app/agents.py、api.py、model_control.py；frontend/src/pages/ChatPage.tsx、components/ExpertRunCard.tsx。

验收：不用手工复制上下文、角色产物互补、必要来源一致、矛盾汇总、一个专家失败时部分交付、全部失败、取消/租约抢占/重启。固定同题集比较单Agent与多Agent，只有可测收益的任务类别默认触发协作。

交付：角色输入输出合同、共享快照审计、选择策略、单/多Agent质量和成本对比。

## 7. M4 深度研究

依赖：M2预算、错误分类与版本绑定；M3可调用的证据审查角色。

1. 分离研究要求、必需来源、来源范围、输出格式和截止条件。显式限制是硬边界；模型规划只能细化，不能覆盖用户限制。一般“官方资料”含歧义时澄清或显示范围假设，不暗自选择特定不可达网站。
2. 复用Source/Evidence，增加必要的原文位置、内容版本和要求引用，建立要求→证据→结论→引用对应。原文匹配校验与语义支撑检查分开：摘录存在不证明推论正确。
3. 正文提取去模板噪声，保留解释段落和相关表格/代码；检索评分关注问题覆盖而非简单关键词堆积。直读指定URL与搜索发现均受来源边界、SSRF和重定向约束。
4. 按明确缺口补检索，只重做受影响章节；不能通过无条件扩大范围或重复全流水线修复。各层重试消耗同一个根预算。
5. 区分COMPLETE/PARTIAL/FAILED/CANCELLED的业务含义，具体编码在迁移设计中与现有状态统一。部分报告列出已支持结论、未解决要求和原因；必需来源不可用不得标完整成功。
6. 验证结论不扩大原文、不错配来源、不把模型建议冒充已执行结果。关键无证据结论在交接计划时明确阻断，不依靠正文免责声明代替机器可读门禁。
7. 余额不足/认证失败停止调用并报真实原因；可重试故障有退避和总上限；取消应及时打断外部调用而非等待整个阶段自然结束。

主要文件：backend/app/research/models.py、web.py、retriever.py、live.py、engine.py、service.py、worker.py；研究页面、进度卡片及计划交接。

验收：冻结多主题离线来源集和可达官方源真实案例；覆盖矛盾资料、资料不足、原文后段关键事实、引用错配、必需来源不可达、永久模型故障、部分交付、预算与取消。保留负面例，禁止靠缩小题目把失败标成原任务通过。

交付：要求覆盖矩阵、可追溯报告、部分完成状态、研究到计划的证据门禁、质量/成本报告。

## 8. M5 自进化

依赖：M1–M4可靠事件与诊断、M2实际bundle绑定、冻结后的专题回归集。

1. 区分观察事实和诊断推断：记录脱敏错误类别、角色、版本、是否截断、网络/计费状态等。仅将可由提示词改善的行为故障送入候选生成；网络、余额、SQL和权限配置问题进入运维/缺陷记录，不生成泛化提示词“修复”。
2. 以根任务、重试关系和输入来源谱系去重；修复前后同题重跑不自动成为多份独立证据。模拟验收数据使用独立标记和分区，既有已知模拟候选保留历史并标记需新版重评，不伪造真实改善证据。
3. 默认使用脱敏元数据；正文回放需要独立授权与可撤销保留策略。授权数据被删除或变更时，相关回放/评测快照应失效，不从审计日志重新拼回正文。
4. 候选只改受影响角色和允许的提示词部分，绑定问题、来源、基线版本、预计指标及风险；未经证据支持的根因不得写成确定事实。自动生成加冷却、失败退避、去重和预算限制。
5. 接入已有不可变suite、DEV/HOLDOUT/SAFETY和paired evaluation。增加原故障回放及邻近场景专题集，不用两个通用问题证明所有候选有效；现有60例发布套件先保持版本，确需变更时新建版本而非原地替换。
6. 目标指标必须改善，关键能力和安全不得退化，成本满足预先冻结上限；同分只算未发现退化，不能自动晋升。独立留出案例不进入候选生成上下文。
7. 审批绑定候选digest、评测报告、权限diff和目标bundle，任何改变均失效。批准后受限Canary，记录实际运行prompt digest；不足样本或待判安全结果禁止晋升。
8. 经批准的门槛触发自动回滚，继续验证在途任务遵循既定版本、未来任务恢复稳定版本。全量晋升另需人工决定；不将“立即回滚演练”解释为充分证明候选有效。

主要文件：backend/app/experience_observer.py、evolution.py、behavior.py、real_evaluation.py、model_control.py、startup.py、api.py；成长页面与候选卡片。

验收：同源重试去重、模拟数据隔离、402不生成行为候选、正文权限/删除、真实故障改善、留出不泄漏、零增益拒绝晋升、预算退避、审批失效、各角色实际灰度命中、样本门槛、自动回滚与重启恢复。

交付：问题与经验账本、角色级候选、故障回放及配对报告、受控发布与回滚演练。当前旧候选不因历史EVALUATED状态直接进入Canary。

## 9. 测试矩阵与阶段出口

| 阶段 | 离线质量检查 | 状态与故障检查 | 真实测试出口 |
| --- | --- | --- | --- |
| M1 | 召回命中/无关注入、事实冲突、摘要归因 | 删除失效、归档死信、恢复、跨作用域 | 长对话记忆与归档核心场景连续3次达标 |
| M2 | 目标/约束保留、路由与预算、实际prompt绑定 | 取消、重启、幂等、上下文不足、模型故障 | 对话→询问→计划修订连续3次无人工修补 |
| M3 | 同题单/多Agent盲评与费用比较 | 子任务部分/全部失败、租约、晚到结果 | 自动装配上下文的协作核心场景连续3次达标 |
| M4 | 原文定位、结论支撑、覆盖与部分交付 | 来源失效、402、超预算、及时取消 | 冻结的多主题研究核心场景连续3次达标 |
| M5 | 故障专题回放、留出、安全、成本和增益 | 谱系去重、审批失效、灰度绑定与回滚 | 经单独批准的真实评测/灰度演练；样本量达到门槛 |

连续3次是流程稳定性最低门槛，不代替统计显著性或Canary样本要求。各阶段只更新其质量断言，不删除旧失败案例获得绿灯。

## 10. 数据迁移与回滚

- 先备份并恢复验证；实施前列出每次迁移涉及的表、字段、状态与消费者，采用Alembic增量迁移。
- 原始消息、现有计划版本、已完成行动、旧失败与审批审计不可改写。新增版本/状态标记表达修订结论。
- Episode、向量、Markdown等派生物按需重建；大规模重算须单独估价和授权。删除/失效先于重建，防止旧数据重新出现。
- 新状态上线前检查所有终态判断、枚举、队列恢复与前端过滤；接口兼容问题用显式版本/映射解决，不暗自改变旧字段语义。
- 应用版本回滚继续使用兼容的PostgreSQL schema；上线后已有新写入时，不以恢复旧备份代替正常回滚。优先停用新行为、保持读取兼容或前向修复；破坏性降级需单独确认。
- 旧进化候选和评测记录只做历史保留，新版发布门槛阻止直接批准；不得把新规则追写成旧评测当时已满足。
