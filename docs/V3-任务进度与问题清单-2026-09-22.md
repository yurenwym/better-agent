## 4. 问题清单

### 4.1 真问题：上一轮的代码缺陷（**已修**）

#### ① Skill 目标判定 1/3 不稳定

同一 Case 连跑三次得 `SKILL`(0.56) / `IGNORE`(0.38) / `IGNORE`(0.31)，
而 JEV 自己的 `repeatable_procedure` 探针三次都给 0.77–0.85——**探针与 choice 自相矛盾**。

**两层根因，都不是采样噪声：**

1. **`target` 问法没有优先级规则。** 一个 Experience 可同时是「可复用流程」和「一般性缺陷」，
   `repeatable_procedure` 与 `decision_behavior_defect` 会同时为真，原 instructions 只说
   "Choose the single surface"，没有 tie-break，模型真的在猜。
   → 改成有序规则链 `(1) SKILL … (4) IGNORE` + 显式 tie-break；`classification_policy` 加
   `precedence` / `tie_break`；探针问法补 "that no reusable procedure captures"。
2. **门禁读错了面。** JEV 返回 `choice`（点估计）/ `probabilities`（闭集分布）/ `confidence`（自报）
   三个面，原实现读 `confidence`。80 例实测：`choice == argmax(probabilities)` 是 **80/80**，
   而 `confidence < 0.5` 有 **5 例**——自报面会压掉分布面本来有信心的正确判定。
   → 门禁改读 `probabilities[chosen]`（新字段 `support`，落库迁移 45 + alembic `20260921_0023`）。

**三方归因（同一 state 的对照）：**

| 契约 wording | 门禁面 | Case B SKILL 命中 |
| --- | --- | --- |
| 旧 | `confidence` | **1 / 3** |
| 新 | `confidence` | 15 / 16 |
| 新 | `probabilities` | **15 / 15** |

**没有调 `min_target_confidence`**（仍是 0.5）。JEV 80 例 `macro_accuracy 0.9625` 不变，SKILL 召回 18/20 → **19/20**。

#### ② 影子验收是假绿

第 1 轮 `no_asset_modified_in_shadow` **通过**，但那轮 skill shadow cycle 全是 `IGNORE`，
压根没走到 target adapter——检查是**空洞的**。分类修好后它立刻变红。

根因：检查口径把「暂存候选」和「生产资产」混为一谈。§41 要求链路跑到 `Candidate → Eval`，
§42 只禁止「0 个**生产资产**被自动修改」。
→ 修法：`asset_snapshot` 只快照生产面（enabled skill versions / live channels / runtime bundle），
并新增 `shadow_chain_reached_the_candidate_stage` 防止空洞通过；固化为单测。

### 4.2 我造成的假问题：三个环境坑（**已查清，非代码问题**）

这一节花掉了两次 90 分钟的全量回归，并两次误判成「新引入的回归」。全部记录在此以免重蹈。

#### ① `--basetemp` 落在 `D:` 盘 → 10 个假失败 + 整轮慢 6 倍

**症状**：全量回归在 7%–15% 区段成片 `F`（`test_agent_worker` / `test_archive_continuation` /
`test_archive_wait` / `test_chat_goal_tools`），整轮耗时从 ~15 分钟膨胀到 90+ 分钟，
而机器 CPU 只有 2.7/16 核在忙——**不是 CPU 饥饿**。

**排除过程（每个假设都做了可证伪的实验）：**

| 假设 | 实验 | 结论 |
| --- | --- | --- |
| 本轮改的迁移 45 引起 | 临时从 `MIGRATIONS` 移除 45 号，重跑同一批 | 8 个失败**一个不少** → 排除 |
| 建库 / 迁移变慢 | 计时 `Database()` | 新建 0.321s（45 条迁移）、重开 0.008s → 不是瓶颈 |
| 并发跑了别的 pytest | 查 `Win32_Process` | 只有一个 pytest → 排除 |
| 磁盘满 | `df -h /d` | 剩 183G → 排除 |
| **basetemp 所在盘** | 同一批 51 个用例只换 basetemp 的盘 | **命中** |

**根因**：本机 `D:` 的小文件 I/O 比 `C:` 慢 **9.2 倍**（实测 30 个 SQLite 小库：
`C:` 0.470s = 15.7 ms/库，`D:` 4.348s = 144.9 ms/库）。`tmp_path` 落在 `D:` 上时，
每个用例的建库成本从 16 ms 涨到 145 ms，于是所有 200–300 ms 预算的用例在**等待开始之前**
就把 deadline 吃光了：

| 观测 | 值 |
| --- | --- |
| `_archiving_states(...) == ["waiting","timeout"]` | 实际 `["timeout"]`（`waiting` 事件根本没来得及记） |
| 原因码 `attempt_exceeded_deadline` | 退化成 `deadline` |
| 状态事件 `waited_ms` / `deadline_ms` | 缺失 |
| `asyncio.wait_for(started.wait(), 1)` heartbeat | `TimeoutError` |
| 同一批 51 用例，C: basetemp | **51 passed / 25.5s** |
| 同一批 51 用例，D: basetemp | **8 failed / 167.9s** |

**为什么会踩**：为了躲开 safe-delete 钩子杀掉 pytest 的临时目录清理，把 `--basetemp` 指向了
「项目内目录」——而项目在 `D:` 盘上。

**为什么改动前的对照轮是干净的**：它**没有** `--basetemp`，用的是默认 `C:` 临时目录
（证据：它末尾 safe-delete 报错路径是 `C:\Users\wym\AppData\Local\Temp\pytest-of-*`）。
两轮唯一的差异就是 basetemp 的盘，不是代码。

> 顺带：正是因为**没有** `--basetemp` 的那些轮次把 `pytest-of-王一鸣\garbage-*` 越堆越多（每轮
> rmtree 都被 safe-delete 掐断），才留下了 §5.3 第二轮那 16.9 GB。加 `--basetemp` 不只是为了躲钩子，
> 也顺手避免了堆积。

#### ② 进度条里的空格填充导致失败清单被错记

从进度条还原失败清单时，把**空格**也当成了用例位。整轮 1837 个用例的进度流里混了 **61 个空格**，
位置因此单调漂移（+5 涨到 +20），足以把失败错记到 `test_db` / `test_learning_agent` /
`test_mcp_acceptance` / `test_recent_window_policy` 等**完全不相干**的文件上，
还让我一度误以为「两轮失败集合不同」——实际两轮进度条**逐字节相同**。

只数 `.EFsx` 之后，位置与 `-rfE` 打出的 node ID **逐个吻合**。工具：`outputs/map_progress.py`。

#### ③ `-rf -rE` 后者覆盖前者

`-r` 只接受一个参数，`-rf -rE` 里后者覆盖前者，汇总里**只剩 ERROR 清单，失败清单静默消失**。
要两个就写 `-rfE`。
