# R1 · M3-01 质量回放与发布门禁

日期：2026-09-19
工具：`backend/app/context_replay.py`（`python -m app.context_replay`）
测试：`backend/tests/test_context_quality_replay.py`（11 项，全通过）

R1 的**硬性验收**。方案明确要求：只测保留量 / 归档次数 / 延迟 / 费用**不能**证明「比现在好」；机制指标改善而质量下降必须判为**不通过**。本文档只回答质量问题。

---

## 1. 为什么不能用机制指标

R1 改的是「压缩后返回给 LLM 的是什么」。机制指标（保留多少字节、归档几次、首 token 多久、花多少钱）都可以在**事实全部丢失**的情况下变好。因此本回放直接测量唯一重要的问题：

> 压缩之后，模型手里还有它需要的事实吗？

---

## 2. 回放设计（确定性、离线、无供应商调用）

| 组件 | 作用 |
| --- | --- |
| 固定夹具 | 7 个事实种在**最旧**的 7 轮里，其后是 220 轮填充，逼迫压缩真正发生 |
| 确定性归档器 | 代替 LLM 摘要器，按主题记录**最新**取值，绝不写入被取代的旧值；输出补齐到接近真实上限（`MAX_SUMMARY_OUTPUT_TOKENS = 1600` 字节） |
| 脚本化探针模型 | 只从**装配好的请求**里找答案，不猜、不补 |
| 竞争上下文 | 真实请求还带 skill(70) / goal(55,required) / plan(50) 三块，它们与历史争同一个预算 |

**关键点**：只有带上竞争的 skill/goal/plan 块，优先级阶梯才会真正起作用。只放历史的话消息层永远有余量，优先级 20 还是 60 都无所谓——那样的回放没有鉴别力。

### 七个探针（覆盖方案点名的每个维度）

| 探针 | 维度 | 期望值 | 被取代值 |
| --- | --- | --- | --- |
| `constraint` | 约束遵守 | 不能超过预算 | — |
| `latest_value` | 最新纠正值 | 8000 | **5000** |
| `confirmed_param` | 已确认参数 | 3 月 12 日 | — |
| `tool_result` | 工具结果 | 553 | — |
| `failed_attempt` | 失败尝试 | A 方案 | — |
| `open_question` | 未解问题 | 住宿还没决定 | — |
| `recent_turns` | 最近几轮对话 | 4 人 | — |

### 判定规则：按**时效**而不是「不存在」

被取代的值只有在**出现在当前值最后一次出现之后**才算污染。原始历史里合法地同时存在「5000」和后来的「8000」，读者按时间顺序解析。必须杜绝的是：**被纠正的旧值活得比纠正它的那句话更久**。

`recent_turns` 探针只存在于**最新的几轮**里，用来单独验证「最近几轮对话」这条通道，与摘要通道解耦。

## 3. 结果

| 变体 | 配置 | 通过 | 装配后大小 |
| --- | --- | --- | --- |
| `reference` | 不压缩 | **7/7** | 76633 B |
| `pre_r1` | 摘要优先级 **20**，预算 23348，`min_turns=0` | **1/7** | 23472 B |
| `post_r1` | 摘要优先级 **60**，预算 23348，`min_turns=5` | **7/7** | 23204 B |

**两个变体用同一个预算**，唯一差别就是优先级修复（以及 `min_turns` 下限）。否则比较会把「改了预算」和「改了优先级」两件事混在一起。

### 决定性结果

```
pre_r1  : 只有 recent_turns 通过（1/7）
post_r1 : 全部通过（7/7）
improved: 6
```

这正是 M2-02 修的 P0：摘要优先级 20 时，它**排在它所替代的原始历史之后**被丢弃，于是在最需要它的时刻正好消失。`pre_r1` 里 6 个来自归档的事实全部丢失，只有不受摘要影响的 `recent_turns` 活了下来。

### `min_turns` 扫描

| `min_turns` | 通过 |
| --- | --- |
| 0 / 1 / 3 / 5 / 8 / 12 | 全部 **7/7** |

`min_turns` 的取值不影响质量——它是**下限**（`test_context_hot_window.py` 单独证明它是下限而非尽力而为），不是质量旋钮。回放证明调大它不会带来退化。

## 4. 计数口径与真实利用率（如实报告）

| 指标 | 值 |
| --- | --- |
| `counted_units` | 23033 |
| `payload_bytes` | 23033 |
| `counted_units == payload_bytes` | **是** |
| 字符数 | 8897 |
| 字节/字符 | **2.589** |
| 预算填充率 | 0.9865 |
| 真实 token 利用率 | **未测量**——需要供应商分词器 |

**结论：字节口径下计数是精确的，不是估计。** 对纯字节层级，`counted_units` 与真实 payload 字节数**完全相等**。

保守性只体现在**相对 token** 的层面：中文场景 2.589 字节/字符，因此字节上界会显著高于真实 token 数。真实 token 利用率需要供应商分词器，**离线无法测量**，这里不做任何声明——**预算填充率不是真实利用率**，不用它冒充。

## 5. 发布门禁与回退

| 要求 | 状态 |
| --- | --- |
| 只对通过 A 级证据的 Profile 小范围启用 | ✅ 开关就是 Profile 的 `validation_tier`。只有声明 `A` + `admitted_context_limit` + `counter_evidence_version` + 已声明 `protocol_budget` 的 Profile 才走 `U_A` 与 A 级预算；其余（`validation_tier` 为 NULL）**完全走原有路径**，行为逐字节不变 |
| 运行中固定 Profile 不原地修改 | ✅ 由 SQLite 触发器 `model_profile_versions_frozen` 强制；迁移 36 重建该触发器并覆盖全部新增列 |
| 关闭新策略可回退 | ✅ 把 `validation_tier` 置回 NULL 即回到旧口径；`history_min_turns` / `compact_ratio` 置空即回到默认策略 |
| 原始消息与 Episode 不删除 | ✅ 已核实：`app/` 内**不存在** `DELETE FROM thread_messages`，也**不存在**任何删除 Episode 的语句；归档只推进 `conversation_archive_state.archived_through_seq` 这个游标，Episode 走 `memory_episodes` 追加写入 |
| 兼容旧 Thread 与旧归档 Job | ✅ 迁移 36/37 全部为附加列 / 附加表，均带默认值；旧 Thread 的 `archived_through_seq` 语义不变 |

## 6. 未完成 / 不声称

1. **真实 token 利用率未测量。** 需要供应商分词器。本回放只报告字节口径的精确性。
2. **回放用的是确定性归档器，不是真实 LLM 摘要器。** 它模拟「被要求记录当前取值的摘要器」这一契约；真实摘要器的输出质量不在本次测量范围内。若真实摘要器漏掉某个事实，本回放不会发现——那是摘要质量问题的范畴，需要在线质量回放。
3. **`reference` 是离线上界，不是线上基线。** 它证明夹具有效、比较有意义，不等于线上表现。
4. 回放不替代既有的 60 例 Evolution 发布门禁。
