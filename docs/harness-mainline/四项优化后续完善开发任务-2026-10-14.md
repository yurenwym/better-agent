## 2. 开发顺序与约束

顺序：B01 → P01—P06 → T01—T07 → W01—W05 → L01—L05 → G01—G02。

依赖：P05 先完成通知身份归属和状态迁移，P06 才接发送；T02 提供统一事件投影后再接 UI；Worker 的完整事件覆盖在 W 阶段补齐，不能在 T 阶段提前宣称全链路完成；L04 删除必须等待 L03 观察门槛。G01 可先验证已经完成的开发范围，G02 必须如实保留观察缺口。

共 **26 个小任务**。每个任务完成一个可检查的纵向闭环，再进入下一项。任务清单默认未勾选，不因测试曾经通过而自动勾选。

### 必须遵守的代码约束

1. Policy 只决策，领域服务写业务状态，TaskRuntime 管执行权；不能复制审批、预算、候选采用或任务状态机。
2. 身份、资源归属、审批、来源、预算和租约来自服务端记录。布尔类型校验不等于可信来源校验；不能把请求 owner 复制到资源 owner 后声称完成授权。
3. 不为“统一”创建通用 Worker 框架、插件注册系统、第二套事件库或所有任务共用的大表。公共代码至少有真实调用方；只服务单一领域的规则留在领域内。
4. 函数签名明确。避免增加任意字典、任意关键字参数和默认允许的安全事实。接口是否合理由生产使用和行为测试证明，不能只靠 isinstance(LeaseRuntime)。
5. 授权读取和实际写入之间有竞争时，使用原事务、行锁或条件更新完成提交前复核；不能仅在 API 入口校验一次。
6. 外部发送无法与数据库原子提交。通知超时、进程崩溃等结果未知情况必须保留 UNKNOWN，不能当作普通失败自动重发。
7. 不改变现有业务审批等级；暂停、取消、撤销必须保持可用，不能因为执行预算不足或任务已取消而拒绝合法停止请求。
8. 复用现有 Event Envelope、Outcome、错误码和脱敏投影。稳定拒绝原因不等于把资源存在性暴露给未授权用户。
9. 状态及其权威事件尽量同事务；投影允许重试但必须幂等。不得以双写两套业务状态保证兼容。
10. 不修改研究算法，不重开 Judge/配对评测支线，不自动部署，不为本文件自动提交或推送。
11. 每项只修改必要文件；不顺手统一格式、重命名大批模块或清理无关历史代码。

**完成**：只有当前版本和有效租约可写向量；同一任务的重试与恢复可通过 Trace 查询，已发出请求不得盲目重复计费。

### [ ] W05 确认通知调度边界并完成 Worker 联测
