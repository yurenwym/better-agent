# 全局 Policy 泛化优化方案

日期：2026-10-13<br>
范围：模型发送、工具执行、TaskRuntime、资产操作和通知发送<br>
目标：让 `PolicyRequest` 真正进入生产调用链，而不是只增加类型定义。

## 一、当前问题

当前已经新增：

- `ActionKind`
- `PolicyPhase`
- `SubjectRef`
- `ResourceRef`
- `VerifiedFacts`
- `PolicyRequest`
- `decide_request()`

但实际调用方仍大量使用：

```python
decide(PolicyInput(...))
```

因此目前属于“契约已补齐，调用方尚未迁移”。另外，当前 `decide_request()` 只读取 `request.facts`，还没有真正使用 `action`、`resource` 和 `phase` 做边界校验。

## 二、开发原则

1. PolicyEngine 只负责纯决策，不直接访问数据库。
2. 服务端适配器负责查询数据库并构造可信事实。
3. 审批不能代替身份、来源、预算和租约检查。
4. TaskRuntime 只负责执行权和租约，不接管领域业务事务。
5. 真实副作用必须在首次执行、重试、fallback 和提交前分别检查。
6. 暂时保留 `PolicyInput` 兼容别名，但禁止新增旧调用。

## P01：固定 Policy 内核契约

### 修改文件

- `backend/app/policy_engine.py`
- `backend/tests/test_policy_engine.py`

### 任务 1：补全动作类型

```python
class ActionKind(StrEnum):
    MODEL_SEND = "model.send"
    TOOL_EXECUTE = "tool.execute"
    TASK_CLAIM = "task.claim"
    TASK_HEARTBEAT = "task.heartbeat"
    TASK_COMMIT = "task.commit"
    TASK_CANCEL = "task.cancel"
    ASSET_READ = "asset.read"
    ASSET_WRITE = "asset.write"
    ASSET_PROMOTE = "asset.promote"
    NOTIFICATION_SEND = "notification.send"
    NOTIFICATION_RETRY = "notification.retry"
```

### 任务 2：补全执行阶段

```python
class PolicyPhase(StrEnum):
    PREPARE = "prepare"
    CLAIM = "claim"
    SEND = "send"
    RETRY = "retry"
    COMMIT = "commit"
    RECONCILE = "reconcile"
```

### 任务 3：让 `decide_request()` 使用完整请求

需要验证：

- action 与 phase 是否允许组合
- resource 是否属于 subject
- resource 的 owner/thread 是否与 subject 一致
- facts 是否为 `VerifiedFacts`

```python
def decide_request(request: PolicyRequest) -> PolicyDecision:
    _validate_action_phase(request.action, request.phase)
    _validate_resource(request.resource, request.subject)
    return decide(request.facts)
```

验收：不合法的 action、phase、resource 组合在发送或执行前被拒绝。

## P02：增加服务端 Policy 适配器

### 新增文件

```text
backend/app/policy_adapters.py
```

### 任务 1：模型适配器

```python
model_send_request(...)
```

负责构造：

```text
subject = owner/thread/turn
resource = model_invocation
action = model.send
phase = send/retry/fallback
```

### 任务 2：工具适配器

```python
tool_execute_request(...)
```

负责验证：

- tool 是否注册
- 当前 run 是否允许该工具
- owner、thread、project 是否一致
- 是否需要审批
- 是否允许写入

### 任务 3：任务适配器

```python
task_claim_request(...)
task_commit_request(...)
task_cancel_request(...)
```

负责验证：

- 任务是否存在
- 当前 worker 是否拥有租约
- lease 是否过期
- 是否已取消
- 是否允许提交结果

### 任务 4：资产和通知适配器

```python
asset_read_request(...)
asset_write_request(...)
asset_promote_request(...)
notification_send_request(...)
notification_retry_request(...)
```

适配器只负责查询和组装可信事实，不执行具体业务写入。

## P03：迁移模型发送边界

### 修改文件

- `backend/app/model_gateway.py`
- `backend/app/model_control.py`
- `backend/app/send_authority.py`

### 必须接入的节点

```text
首次发送
重试前
fallback 前
结果提交前
```

每个节点都调用 `decide_request()`。

### 验收场景

1. 预检通过后撤销来源，模型调用次数为 0。
2. 第一次请求失败后撤销来源，重试调用次数不增加。
3. 取消事件发生后，不再发送下一次请求。
4. root budget 耗尽后，不能通过 fallback 继续发送。

## P04：迁移工具执行边界

### 修改文件

- `backend/app/tool_executor.py`
- `backend/app/chat_tools.py`

### 任务

将以下逻辑从旧的 `PolicyInput` 调用切换到 `tool_execute_request()`：

- capability 是否注册
- skill 是否允许
- identity 是否有效
- approval 是否已授予
- tool write 是否需要 reconciliation

审批只设置：

```text
approval_granted = true
```

不能用审批绕过其他边界。

### 验收场景

- 跨 owner 调用被拒绝。
- 跨 thread/project 调用被拒绝。
- 旧版本工具调用不能提交新版本结果。
- handler 没有执行时，不产生写入或 reconciliation 假状态。

## P05：迁移 TaskRuntime 边界

### 修改文件

- `backend/app/task_runtime.py`
- `backend/app/research/service.py`
- `backend/app/agents.py`
- `backend/app/conversation.py`

### 统一覆盖

```text
claim
heartbeat
require_lease
finish
recover_expired
cancel
```

### 约束

TaskRuntime 只判断执行权，不负责：

- 研究报告业务状态
- 专家成果业务状态
- 计划物化事务
- Learning checkpoint
- Promotion 事务

### 验收场景

- lease 丢失后不能 commit。
- 取消后不能继续发送。
- 过期任务重新领取时使用新的 epoch/attempt。
- 重试不创建新的 root budget。
- 结果提交与终态事件在同一事务完成。

## P06：接入资产和通知操作

### 修改文件

- `backend/app/learning_assets.py`
- `backend/app/learning_promotion.py`
- `backend/app/notifications.py`

### 资产操作

接入：

```text
asset.read
asset.write
asset.promote
```

Learning 仍保留自己的：

- checkpoint
- learning budget reservation
- source validation
- canary/promotion transaction

### 通知操作

先补齐 delivery 状态机：

```text
PENDING → SENDING → SENT
                  ↘ RETRY_WAIT
                  ↘ FAILED
```

确认 provider 幂等和未知副作用语义后，再评估是否由 TaskRuntime 托管。

不能直接把通知当成普通模型任务自动重试。

## P07：清理旧调用

### 检查命令

```powershell
rg -n "PolicyInput\(" backend/app backend/tests
```

### 删除条件

- `backend/app` 中旧调用归零。
- 所有真实边界都使用 Policy Adapter。
- 模型、工具、任务、资产、通知均有副作用测试。
- 旧兼容测试不再代表生产路径。

然后再删除：

```python
PolicyInput = VerifiedFacts
```

## P08：测试门槛

### Policy 内核测试

- action/phase 不匹配
- resource/subject 不匹配
- 来源失效
- 预算耗尽
- 取消
- 租约失效
- 审批缺失

### 边界适配器测试

- model send
- tool execute
- task claim/commit
- asset read/write/promote
- notification send/retry

### 实际副作用测试

不能只断言返回 `DENY`，还要断言：

- 模型网关调用次数为 0
- 工具 handler 未执行
- Worker 未提交结果
- Learning 资产版本未变化
- Notification provider 未收到请求
