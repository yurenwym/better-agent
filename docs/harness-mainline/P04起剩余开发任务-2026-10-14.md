## 一、主要做什么

目标是把现有“对话 → Agent 调用工具 → 任务执行 → 返回结果”这条主链路补齐为可控制、可追踪、可恢复的闭环。沿用已有业务功能和 Harness，不新增研究评测平台。

| 工作 | 用普通语言解释 | 用户能获得的效果 |
| --- | --- | --- |
| Policy 剩余接入 | 读取记忆、保存资产、采用学习结果、发通知时，执行统一的权限和来源检查 | 被撤销的内容不能继续使用，未授权操作不会落地 |
| Trace 与页面 | 把一次对话关联的模型、工具、任务和后台事件放在同一个轨迹里 | 能看到卡在哪一步、为什么失败、是否已产生外部效果 |
| Worker 收口 | 给后台摘要、向量、学习和通知补齐明确的执行权及恢复规则 | 服务重启或任务超时后能安全处理，旧进程不能覆盖新结果 |
| Legacy 清理 | 先确认旧代码还有没有人在用，再显式关闭并分批删除 | 减少两套逻辑并存造成的行为差异和维护成本 |

其中“资产”指项目已经存在的记忆、技能、提示词/行为版本等数据；“学习采用”指现有候选通过审批与质量门槛后启用。本计划不扩大这些功能的产品范围，也不新增 RAG 功能。

## 三、统一实现约束

1. 一个业务状态只有一个权威写入者：Policy 决策，领域服务更新状态，TaskRuntime 管执行权，Trace 负责读取和展示。
2. 用持久化记录校验身份与资源归属；不接受模型提供的 owner、lease、审批凭据或预算权限，不给缺失身份自动填 local-user。
3. 校验必须靠近实际副作用；涉及竞争时在原事务中复核，不能只做 API 预检查。
4. 公共抽象必须有实际调用者。不新建通用 Worker 平台、万能任务表、第二套审批或事件存储。
5. 保留现有质量、成本、来源、checkpoint 和审批规则；统一接口不能替代领域不变量。
6. 通知发送结果未知必须保留 UNKNOWN；没有幂等保证或可靠对账时，不自动重新发送。
7. 代码使用明确参数与类型、单向依赖、小函数。不要为压缩行数牺牲可读性，也不要顺手整理无关模块。
8. 关键状态和权威事件同事务；投影幂等。事件只记录必要低敏字段，不存密钥、完整 prompt 和模型内部推理。
9. 中间任务只跑有针对性的测试；阶段完成及准备提交时跑完整门禁。不要用删除断言、增加 skip 或虚假完成标记获得通过。
10. 不自动部署、推送、启动付费评测或改变产品审批等级。
