### 1.1 执行范围收缩：第一版只修预算主链

前述目标是最终方向，不再把 14 个任务作为同一次发布的串行前提。最先交付 R1，只解决已确认的固定 12,000 与完整请求计数问题，复用现有 Episode、归档租约、事务和错误处理。R1 不新建 Facts 生命周期、活动 manifest 或恢复补读状态机，也不实现自适应 G。

| 发布 | 范围与边界 | 前置 | 发布价值 |
|---|---|---|---|
| R1 预算修复 | T00-A 最小证据、必要 Profile 字段、A级计数、完整请求预算、移除热窗口固定限制、相关回归 | 无其他新机制 | 大窗口能获得更大的保守工作预算；未达实际预算压力不提前归档 |
| R2 容量与延迟改进 | 工具结果投影、N/R 双约束、基于现有 Job 的静态提前归档/限流、等待提示与可取消性 | R1 | 提升大工具结果与长对话的可用性；仍复用现有归档提交机制 |
| R3 可选效率优化 | B级估算、有限 G 迭代；按实测收益选择启用项 | R1；G 优化需要 R2 数据 | 提高真实 Token 利用率、减少等待；不是 R1/R2 的阻塞项 |
| R4 按需求单独立项 | Facts、候选 manifest CAS、恢复补读及确定性证据门控 | 有明确质量/恢复需求和各自验收 | 支持复杂任务恢复；不能为了上线预算修复提前全做 |

R1 拆成 3 个可审查提交：

1. **预算契约**：定义 A/C/S/O、A级计数版本与协议开销，Profile 只增加本期必需字段；测试 A 小于 C、C 未知及无证据拒绝。B/G/Facts 等字段不预建空框架。
2. **调用链修复**：先构造本轮完整候选再计数；动态分配剩余历史空间，删除固定 12,000 和固定 80% 对热窗口的生产约束；**归档触发线与保留量必须同源**——`ConversationArchiver.keep_tokens`（memory_archive.py:79）默认 12,000 且 startup 未覆盖，`_select_archive_prefix`（:552）用它算 `archive_count`，若只抬触发线不改保留量，一次归档会把 12,000 以上历史全部压掉；R1 归档目标量取 `compact_target = ceil(compact_ratio × H)`，ratio 由 Profile 提供（初始候选 0.7），选择器内不得留绝对字节常量。仅实际需要归档时走已有归档器，提交失败仍不推进原覆盖游标。摘要批次预算按摘要模型的独立预算配置，不与会话热窗口共用数值。
3. **回归和灰度**：验证 32K/64K/较大 Profile、完整工具 Schema、无提前裁剪、调用配对、最终上限、归档失败不丢来源及旧数据兼容；报告A级实际利用率和提前归档减少量，带一个策略开关小范围发布。

R1 明确不承诺已经解决同步归档时延、任意大当前 Turn 或缺失历史后的自动恢复，沿用既有行为并记录为 R2/R4 待办。不得把这些未实现能力写入 R1 完成声明。每期只测试/评审其启用机制，完整十对交互仍是 R4 同时启用全部机制的前置要求。

## 2. 前置验证、配置与误差预算

### 2.1 T00 的两级通过标准

先核实实际 DeepSeek 端点、模型 ID/可识别版本、最大总上下文、输出/推理 Token 口径以及代理额外限制；再决定工作窗口。不得依据模型名称或旧版 tokenizer 推断当前规格。

官方规格入口：[DeepSeek 模型文档](https://api-docs.deepseek.com/quick_start/pricing/)。本版不把未经验证的容量整数写为生产默认值，也不预设是否存在可匹配的官方 tokenizer。

T00 是按 Profile/端点判定的两级能力门禁，不是整个项目的单点开关：

| 等级 | 必须具备的证据 | 允许做什么 | 不允许声称什么 |
|---|---|---|---|
| T00-A 保守可用 | 模型/端点身份；有证据的可用工作容量；单位一致且适用范围明确的保守计数；输出预留有效；代表性请求可发送 | 交付 R1 保守预算修复；R2 可在额外验收后启用静态提前量，不要求完成全部 T 任务 | 不声称已知真实最大窗口、统计 P99 或高利用率能力 |
| T00-B 校准可用 | A 全部证据，加独立验证集误差报告、时延/增长样本、适用域和越界处置验证 | 启用校准估算；在 §3.1 收敛和 T11 验收后启用自适应提前量及较高利用率 | 经验误差包络仍不是任意输入的理论保证 |

B 不要求官方给出精确最大整数；经探测验证的工作上限也可以在限定范围内完成校准。A 和 B 都必须记录容量证据是官方规格、代理配置还是实测准入范围。

A 未通过时仍可做代码审计、配置迁移设计、mock 和回放框架，不阻塞其他已通过 A 的模型。只暂停该未经验证 Profile 的新发送策略发布。已经有可核验成功记录和保守预算的旧 Profile 可评为 A，不能仅凭仓库里存在一个默认数字就算通过。

T00-A 报告至少包含证据来源/日期、可用容量、输出口径、计数器/内容适用域和固定运行限制；T00-B 增补误差分布、独立验证、摘要及主调用时延、增长样本。B 未完成不妨碍 A 模式交付。

### 2.2 误差进入公式，而不是固定加 4K

```text
C = 已核实的模型真实总窗口；未知则为空，不能填入猜测值
A = 有证据的准入工作容量（admitted_context_limit）
S = min(产品总工作窗口上限, A, C 若已知)
O = 输出预留，且不小于本次请求允许的输出
H = S - O                              # 完整输入容量
E = 完整请求的原始 Token 估计
A级：U_A = byte_bound(request) + protocol_bound(request)
B级：U_B = ceil(alpha * E + beta)
U = 当前启用模式对应的完整输入预算计数
发送条件：U <= H
```

- B级 alpha >= 1 覆盖随输入增长的低估偏差，beta >= 0 覆盖协议包装和固定偏差；A级不依赖尚未完成的 alpha/beta 校准。
- 在校准集拟合低估包络，用独立验证集检验；报告样本量、长度/类型范围、P95/P99、最大观测低估和越界次数。
- 样本不足以支持 P99 时明确写“证据不足”；经验包络不能称为对未来任意输入的理论上界。
- 只有匹配 tokenizer 且完整协议开销得到验证时，才能收紧包络；使用 tokenizer 不等于完整请求精确计数。
- 请求超出校准长度、内容类型或模型版本时，切换到经验证的保守计数。不存在可靠回退则不发送该类大窗口请求。
- UTF-8 字节上界仅在 tokenizer 与协议假设成立时使用，不默认适用于多模态或遗漏的包装开销。
- beta 已包含的开销不得再次从 H 扣除；触发线、近期预算、压缩收益统一使用 U 口径。

示例：E=100,000，若验证得到 alpha=1.10、beta=1,000，则预算计数为 111,000，而不是只加 4,096。这些系数仅说明算法，不是 DeepSeek 实测值。

收到服务端 context overflow 时，记录校准越界，允许一次重建后的重试；相同请求不得无限重发。暂停该 Profile 的高利用率路径，运行时切到更保守的计数，不原地篡改固定 Profile 版本。

#### A级的具体实现与适用范围

复用现有 `Utf8UpperBoundTokenCounter.count_payload(messages, tools)`，保持其规范化 JSON 与 UTF-8 字节统计口径。定义：

```text
byte_bound = len(canonical_json(messages, tools).encode("utf-8"))
protocol_bound = b0 + bm * message_count + bt * tool_definition_count
                 + bc * tool_call_count + br * tool_result_count
U_A = byte_bound + protocol_bound
```

此处字节数用于构造 Token 上界，不是把字节说成真实 Token。前提是目标文本 tokenizer 不产生比其输入 UTF-8 字节数更多的普通文本 Token，且有版本化的协议包装边界证据；模板额外项须补入 `protocol_bound`。b0/bm/bt/bc/br 是该适配器经验证的非负保守上限，不来自B级回归拟合；必须记录单位、覆盖的包装项及来源，未知不能默认为 0 或任意写 4096。

JSON 标点本身可能使 byte_bound 高估，R1 不尝试扣掉这种重复保守量来提高利用率。隐藏模板无法获得可信边界时，允许以完整请求的限定样本验证建立“经验保守模式”，但须标识该强度而非声称证明了理论上界；限定消息/工具数量、输入类型和长度，越域拒绝或复验，违反实测边界立即停用。连经验保守证据也没有则该适配器不通过 A，不能靠将 alpha=1、beta=0 伪造通过。

R1 只承诺经过验证的文本和工具 JSON；图片、音频及其他隐含计量必须另有专用上界，否则不纳入这个计数器。

#### A级利用率与上线收益如何评估

```text
保守效率 q = 服务端 actual_prompt_tokens / U_A
真实窗口利用率 eta = 服务端 actual_prompt_tokens / H
计数填充率 f = U_A / H
因此 eta = q * f
```

不能仅凭“A级字节计数”给出统一的真实利用率区间。比如某类样本 byte_bound 约为实际 Token 的 2–5 倍、协议开销较小，则填满 U_A 预算时真实利用率约为 20%–50%；这是条件示例，不是 DeepSeek 的预期实测结论。实际报告按中文/英文/代码/工具分别列 q 与 eta 的观测 P10/P50/P90、样本量和长度范围；少量样本只报告观测区间，没有 usage 则标为未知，不捏造百分比。

R1 的收益主要是取消固定 12,000、统一完整请求计数和使预算随模型/Profile 变化；不会自然获得B级高利用率。上线决策比较同一数据集中新旧保留的原始轮次/字节、提前归档次数、调用失败率、延迟与费用；若保留量无改善或成本/延迟超过预先约定门槛，就不扩大灰度，不把“计数填充率变高”当作真实利用率提高。

### 2.3 扩展现有 Profile

| 字段 | 含义 |
|---|---|
| context_window | C，对应真实 context_limit；未知时必须可明确表示未知 |
| admitted_context_limit / capacity_evidence | 实际准入上限 A，以及官方/代理/实测证据、适用域和日期；不得冒充真实最大窗口 |
| validation_tier | T00-A 或 T00-B；决定可启用的计数和调度模式 |
| max_output_tokens | O，对应 output_reserve；请求输出不能超过它 |
| soft_context_limit | 产品总工作窗口上限；唯一生效公式 S=min(soft_context_limit, admitted_context_limit=A, context_window=C 若已知)，A 永远不能省略 |
| token_counter_id/version | 计数实现及固定版本 |
| calibration_version | B级 alpha/beta、适用域与验证报告版本；A级改用 counter_evidence_version 关联字节/协议上界证据 |
| recent_turns_max | 优先保留的完整历史 Turn 数，候选初值 5 |
| recent_token_cap | 近期原文预算上限，由 H 推导并经回放选择 |
| background_headroom | 预留给后台摘要完成期间的增长空间 |
| rearm_growth | 摘要后希望容纳的新增内容量，形成迟滞 |

Job 时限、前台等待与后台并发属于一个版本化运行策略，Profile 引用它，不重复维护多份 UI 参数。

所有上下文构建器、归档器、fallback 和最终 Gateway 只调用同一个 `effective_input_budget(profile)` 入口，不能各自重写 min 公式。必须测试：C=128K、A=64K、soft=128K 得 S=64K；C 未知、A=32K 得 S<=32K；A 缺失或无有效证据时不能自动退为 min(soft,C) 绕过门禁。

128K 只能是产品上限候选。模型真实窗口或已验证准入上限若为 64K，则 S 不超过 64K，再扣 O，重新推导所有阈值；不存在独立写死的 100K/50K 配置。显式无效输出配置拒绝保存，不能静默扩大模型能力。

### 2.4 规格不明确时的 Plan B：有界容量探测

探测是 T00 的可选验证路径，不在本次文档修订中实际调用。使用专用无敏感测试输入、关闭工具副作用，并在已有调用授权与明确费用/请求数预算内运行。

1. 固定端点、模型、消息/工具格式和生产输出预留 O；要求短回复可以降低实际输出费用，但不能擅自降低 O 再外推原生产窗口。
2. 从有成功证据的小输入起步，用中英文、代码、工具 Schema 等多类样本扩大输入，找到成功点 L 与明确容量拒绝点 F。扩容与二分共用最多 16 次请求的初始预算，另设总费用和时间上限；上限到达立即停止。
3. 只有明确的上下文超限错误才构成 F。超时、429、服务错误、HTTP 请求体大小限制均单独记录，不能当作模型 Token 边界；网关大小限制仍应限制该端点的准入请求。
4. 在同一模板族且局部表现为单调时，对 [L,F) 二分；区间缩小到 `max(1024 Token, 2% × L)` 或耗尽预算即停止。发现非单调、服务切换或计数不稳定则终止边界推断，保留已验证成功点。
5. 优先使用服务端 usage/错误中明确且一致的 Token 口径记录输入与输出预留，不把字符长度、请求字节或有低估风险的估计当作真实 Token 边界。
6. 将结果写为限定端点、格式和输出预留的经验区间，不写成“模型真实最大窗口”。初始准入候选最多取各样本族成功容量下界的 80%，再在候选附近做独立样本验证；80% 是探测降额候选，不替代计数误差包络。
7. 未找到 F 也可以基于经过验证的 L 进入 A，无须追到最大容量。无法获得单位一致容量证据或候选验证失败时，保持此前有证据的更小准入上限；完全无证据则该 Profile 不通过 A。

探测产物包括每次输入/预留输出口径、错误分类、接受/拒绝区间、预算消耗和版本指纹。端点版本改变或出现更低容量拒绝时，暂停高利用率，降低准入范围并复验，不能把一次探测当作永久能力证明。

## 3. 压缩目标：由增长量与迟滞推导

```text
G = 摘要完成时间内的高分位增长 + 一次有界输入突增余量
B = H - G                      # 后台准备触发线
D = 希望容纳 k 次后续调用的增长量
T = B - D                      # 本轮完整输入目标
约束：0 < T < B < H
```

T00-A 使用固定有界批次与静态提前量：初始实验候选 `G0=30%×H`、`D0=20%×H`，即 B0=70%×H、T0=50%×H，经保守模式回放后才启用。这是冷启动运行策略，不声称预测了摘要 P95，也不把 2:1 比例固定为长期目标；不满足 `0<T<B<H` 或硬保护条件则调整/停用该候选。

T00-B 可使用摘要 P95 耗时、实际增长轨迹和投影上限推导 G，但必须经过下面的有界迭代。任何模式都不能保证覆盖任意突发输入，最终 H 检查和恢复路径始终有效。

D 需要比较质量损失、触发频率、费用和延迟。第一轮回放可比较 H 的 10%、20%、30% 三档带宽，作为实验参数，不作为未经数据验证的生产默认。

每次只压缩能达到 T 的最小完整前缀。若完整输入为 100K，希望多容纳约 15K 增长，可评估目标 85K；没有理由一律降到 50K。摘要后实际重建计数，硬保护部分大于 T 但小于 H 时允许未达目标。

防抖与成本要求：

- 同一来源快照只保留一个 Job；新增长合并到下一批，不重复排队。
- 提交后新增足够未覆盖内容才常规重触发；容量紧急情况可绕过冷却，不能绕过 Job 去重。
- 没有可压缩内容或收益太低时停止重复摘要，转引用投影/恢复流程。
- 摘要输入批次、输出和总工时单独设预算；只发送待压缩来源及必要锚点，不发送整份 100K Prompt。
- 摘要输出上限经质量/时延回放选择，不默认每次生成 4K–8K。

### 3.1 G/T 的离线有界迭代

承认这是一组相互影响的参数，不把“离线回放”视作自动收敛。先固定模型/计数版本、工具投影上限、单摘要批次输入与输出上限、并发、Job 截止时间和一次 D 候选，再迭代 G；更改这些固定项需要新一轮评估。

1. 从通过保守回放的 G0 开始，计算 B0/T0，选最小待压缩前缀。
2. 执行回放并测量从排队到产生可采用候选的总耗时，包含所有批次、重试和 CAS 冲突成本，不能只测单个 LLM 请求。
3. 将该耗时窗口映射到增长轨迹，得到带突增余量的 G_required；保守更新 `G_next=max(G_current,G_required)`，避免测量噪声使提前量上下抖动。
4. 连续两次更新的 `abs(G_next-G_current)/H <= 5%`，且验证集无“已建模增长抢先耗尽余量”、符合 Job 时限和质量门槛，才接受为操作性收敛。5% 是评估容差，不是理论收敛证明。
5. 每个 D 候选最多 4 轮，并受真实调用预算限制；参数不合法、无有效压缩收益、质量失败、样本不足或预算耗尽均停止。不同 D 分开评估，不在同一迭代中同时改所有变量。

不收敛不阻塞基础功能：保持或回退通过验收的 T00-A 固定策略，限制批次、速率和费用，超限走有界恢复。没有通过回放的静态策略时仅暂停该 Profile 的后台自适应发布，继续修正离线策略；不得靠无界增加 G 或无限请求模型求收敛。

## 4. 近期历史：N 轮与 Token 双约束

### 4.1 最小硬保护

硬保护：System/权限、当前用户指令、明确用户约束、执行前置事实、必要 Task State、正在执行的参数和未闭合工具调用依赖。

整个当前 Turn 不应永久硬保护。其已完成工具结果、日志与旧过程片段可转成有界引用。未完成调用保持 ID、参数及协议合法性；闭合工具链可以整体替换为有来源的摘要。

普通历史事实按当前任务相关性投影；只把当前约束和执行前提作为硬保护，避免 Facts 变成另一份无限历史。

### 4.2 选择算法

```text
N = recent_turns_max                  # 初始候选 5
P = 硬保护 + 必需摘要预留 + 必需包装开销的预算
R = min(16384, floor(0.25 * H), max(0, T - P))

先持久化大工具原文，并用有界投影参与预算。
从最近完整 Turn 向前选连续后缀：轮次 <= N 且近期预算 <= R。
其他完整历史加入可压缩候选，不直接静默删除。
```

块预算仅作规划，最终必须统计完整请求 U。R 是近期原文保留承诺上限，不是新的提前裁剪热窗口：摘要未完成且全量装得下时，仍发送其他原始历史。

上式展示初始配置的生效值；16K 和 25% 必须作为版本化策略参数保存，不写死在选择器中。`recent_token_cap` 对应绝对上限，比例上限和 N 一起接受回放验证。

最近 5 轮达 90K 时：先投影工具结果，再从最老近期轮次释放软保护，纳入压缩。单个最新轮次超过 R 时不跳过它去回填更旧的小轮次，而是分离硬保护指令与已完成过程内容，保留工具链完整性。

只有不可缩减指令/权限/必要协议本身超过 H，才是真正不可发送。此时保留输入，支持分段处理或携带任务状态开启新上下文，不将 Thread 永久置为失败，也不假装能无损容纳无限输入。

### 4.3 为什么初始 N=5，如何替换

5 没有模型理论依据，仅是 3/5/8 三档实验的中间起点，意图覆盖短距离澄清、纠正和工具问答；不能称为已验证最优。R 的 16K/25% 同样属于初始工程候选，K=1024，均使用 U 的预算口径。

在相同 R、计数器和压缩策略下回放 N=3、5、8，比较指代解析、近期纠正保留、工具链完整性、压缩频率和时延。硬性约束/执行前提不得丢失；发布前指定语义质量非劣容差，选择满足门槛的最小 N。5 未通过就不得沿用，保守模式可使用已通过回放的其他 N。

记录“轮次限制先命中”与“Token 限制先命中”的比例；若长期由 R 决定，不必为 N 增加自适应控制器。N 只影响软保护，完整请求装得下时不据此裁掉更多历史。

## 5. 后台优先与前台恢复 UX

### 5.1 常态不等待摘要

Turn 完成或工具链闭合时评估稳定快照；达到 B 或预测下一次接近容量时，后台准备最小必要旧前缀的候选 Episode。每次调用前仍检查本轮实际完整请求。

后台完成只保存候选，不立即改变正在使用的视图；下一调用边界校验后采用。后台不持有整个对话生成锁，不中断流式回答，设低优先级并发/速率配额，主调用优先。

已有合格候选且本次仍存在压缩需求时，即使尚未超 H，也可以在调用边界采用，以获得迟滞空间；不能一直等到硬上限才读取后台成果。采用前重新构建并计数、验证当前来源和事实/状态依赖，随后以预期版本 CAS 激活；并发新增事件保留在覆盖范围之外。

U<=H 时直接使用当前可用完整视图发送，即使超过 B，也只幂等入队，不 await 摘要。必须测量共享限流造成的干扰，不能把“异步”直接当作“无延迟”。

### 5.2 突然超限的有界处理

每一步后重建计数：

1. 去重并移除低相关可选检索内容。
2. 用有界工具投影替换已持久化大结果，限制非必要工具 Schema。
3. 采用来源及事实/状态版本匹配的已完成候选。
4. 若已有相关 Job 接近完成，有限等待并显示状态；不从零在前台跑长摘要。
5. 等待到期构建显式恢复视图：当前指令、约束、权威状态、已验证摘要、缺口范围与来源读取引用。覆盖游标不推进。
6. 恢复视图只处理当前信息充分的问题；需要缺失来源时进入 §5.4 的有界补读状态机。依赖缺失决策的操作暂停到相关来源恢复，不能假装已知历史继续副作用操作。

恢复视图不是“压缩成功”。UI 提示正在整理历史，可继续输入；依赖特定历史的操作显示等待原因。支持取消等待和发送新消息，旧 Job 根据新版本决定是否仍可用。

若恢复视图仍超限，进入可恢复的输入拆分/任务交接状态。普通历史增长不应走到这个边界。

### 5.3 第一轮验收目标（待实测）

- 常态调用等待摘要时间为 0，比较后台开/关时模型首 Token 的 P50/P95。
- 本地预算/投影新增耗时 P95 目标 <=200ms，未达先优化。
- 需要等待时 1 秒内显示状态，初始前台等待上限候选 2 秒，到期进入恢复流程。
- Job 有独立截止时间和最多一次受预算约束的重试；后台慢不延长前台等待上限。
- 状态提示时间与真实模型首 Token 分开统计，不能用提示掩盖首字退化。

### 5.4 补读不递归：限定工作区、轮数与退出条件

补读是恢复阶段的有限状态转换，不是“读到装得下为止”。只有最小恢复视图已通过容量校验，才开始读取；基础视图本身不合格则直接进入可恢复等待，不启动补读。

第一版候选限制：每个恢复 epoch 最多 2 次范围读取；每次投影不超过 2K；累计返回不超过 `min(8K, 10%×H)`；补读阶段总时限 2 秒，包含失败或缩小范围后的重试。与已有候选等待合计的附加等待最多 4 秒，不包含随后正常回答生成时间。参数需经 T11 校准，不视为已测 SLA。

读取前从剩余空间分配工作区：先去除非必需片段，预留工具调用/结果包装，再按完整 U 预测可容纳片段大小。不足以容纳最小有用片段时不发起读取。读取采用范围/字段接口，不读完整 Artifact 后再期望摘要器救场。

返回后先在上下文外持久化完整读取结果，选择有界原文片段替换工作区中的旧非必需内容，不无限追加。每次都重新校验完整请求；超过 H 时拒绝本次注入，剩余次数允许则缩小范围，否则暂停。保留的工具协议记录、事实和硬约束都计入预算，不能为了释放空间拆散调用链。

| 当前状态 | 条件/事件 | 下一状态与动作 |
|---|---|---|
| RECOVERY_BASE | 基础视图自身超限 | WAITING_INPUT，保存输入与检查点，不调用模型 |
| RECOVERY_BASE | §5.5 程序门控返回 ALLOW | READY，仅执行获得明确准入的操作/受限回答模式 |
| RECOVERY_BASE | 依赖缺失且有次数/时间/空间 | READING，选择确切来源范围 |
| READING | 来源有效、注入后可容纳且前提满足 | READY，重新校验版本后继续 |
| READING | 还缺来源但仍有预算 | READING，允许下一次不同范围或更小读取 |
| READING | 超限、无进展、预算耗尽或来源缺失 | WAITING_SOURCE，保存检查点并停止本轮补读 |
| WAITING_SOURCE | 相关候选完成或来源可用 | 重新验证检查点，可恢复；不自动授予无限新读取额度 |
| WAITING_INPUT | 用户补充有效信息/输入拆分完成 | 新调用边界重建，重验容量和前提 |

同一 source/version/range 的重复读取或未减少缺失前提视为无进展。使用 source snapshot、任务操作和 Profile/事实版本绑定恢复 epoch，持久化尝试次数；同一无变化快照的自动重试不得重置次数。真正新增来源、有效用户补充或已完成摘要才允许新的有界恢复 epoch。

无论停止在哪个等待状态，Thread 都能接收新消息，独立问题仍可处理。涉及缺失前提的动作不能继续；补读工具本身不能递归触发压缩或重新调用同一恢复入口。

### 5.5 恢复态的判定责任（仅 R4，R1 不实现）

不存在能靠几条规则证明任意自然语言问题“证据充分”的通用函数。删除泛化的 `needs_source_for_next_action(view)` 授权语义，改成服务端 `evaluate_source_gate(action_contract, context_snapshot)`，返回 ALLOW、NEED_SOURCE 或 UNDETERMINED，含缺失前提 ID 和理由。

| 请求/操作类型 | 判定者与规则 | 可放行范围 |
|---|---|---|
| 已登记结构化工具/业务操作 | 执行服务按 action_contract 校验所需参数、owner/scope、授权、状态版本、事实版本与确切来源范围是否齐全、当前且无冲突 | 仅该操作；实际执行前再次校验，不能转授给后续任意操作 |
| 精确字段读取/原文摘录 | 读取服务验证确切实体/字段、来源完整性、权限；服务端模板或受限字段渲染 | 只展示读取结果，不生成额外历史结论 |
| 自由文本问答且存在历史缺口 | 程序默认 UNDETERMINED；模型自报“独立问题/信息充分”不能改成 ALLOW | 显示恢复状态，补读或让用户明确指定独立的新任务范围；不进行依赖旧历史的开放式回答 |
| 用户明确另起独立任务 | 业务层建立明确新任务作用域，保留全局/权限约束，原任务仍暂停 | 作为新的普通任务处理，不声称修复了原任务的历史缺口 |

action_contract 来自代码中登记的工具/业务定义，包含参数及状态前提、来源关联和验证器；模型只能建议操作/候选来源，不能生成自己的契约、删减 required_sources 或用 confidence 放行。未登记契约或未知依赖返回 UNDETERMINED，不默认为无需来源。

确定性校验能证明已登记前提是否满足，不能证明源文本必然蕴含任意新结论。若某操作依赖尚未结构化的语义决定，仍返回 NEED_SOURCE/UNDETERMINED，恢复完整相关范围或获得明确业务确认后再处理，不能只因引用 ID 存在就认定结论正确。

门控结果绑定 invocation/action、manifest/source snapshot、Profile、事实/状态版本；任一改变即重验。R1 不承担上述状态机：仍使用原归档成功后的上下文，归档失败保持现有错误处理，绝不新增“截掉历史也继续回答”的捷径。

## 6. Critical Facts：最小范围和可执行契约

### 6.1 字段归属与写入者

| 内容 | 权威来源 | V1 处理 |
|---|---|---|
| Goal/Todo/进度/动作结果/资源状态 | 现有任务、工具记录 | 原业务服务写，上下文只读投影 |
| 权限与作用域 | 认证/运行时策略 | LLM 不可写 |
| 已结构化确认的参数/约束 | 用户输入、Ask 答案 | 白名单业务处理器校验后写 |
| 自由文本约束 | 原始用户消息 | 保留原句来源；模型可提候选，不自动确认 |
| 推测根因或因果结论 | 来源证据与模型候选 | proposed，不提升为 verified |

工具“成功”只能证明其契约中的结果，不证明模型推断的根因。V1 不做通用语义事实推理；自动提取后置，不阻塞核心压缩。缺少结构化 Fact 时，关键用户约束以原始来源锚点保留，不能因未抽取就丢失。

### 6.2 存储与写命令

最小字段：fact_id、scope、key、value、source_refs、writer_type、status、version、supersedes_id。复用可满足要求的现有存储，否则只增加最小表，不复制 Task State 字段。

- propose：LLM 可提出候选，状态为 proposed。
- confirm：仅可核验的明确用户确认或白名单验证器执行；引用存在不等于语义被证实。
- supersede/invalidate：必须携带目标 ID、预期版本及新来源，事务比较版本；冲突重读。
- 校验来源作用域、原消息/字段值和写入者身份；LLM 不能自报 writer_type 绕过确认。
- 同一 scope+key 最多一个无冲突的当前 confirmed 值；后来出现的候选不能覆盖它。
- Task State/权限相关类型不允许通过 Facts API 写入。

### 6.3 用户纠正判定

1. 结构化更新明确 key/fact_id：验证作用域后，将旧值 superseded，新值 confirmed。
2. 受控解析器能无歧义识别白名单字段：保留用户原句，按业务更新契约处理，不依赖 LLM 自报 confidence。
3. “不是那个”等模糊纠正：创建冲突候选，不覆盖旧值；保留当前原句，只有依赖冲突值的操作需要澄清。
4. 未解冲突阻止相关自动操作，其他独立对话继续。
5. 明确纠正使依赖旧事实版本的候选/缓存失效，下一请求解析当前有效值；不能只检查旧原文哈希。

必须测试端口 5432→5433、模糊指代、助手建议被重复、伪造来源、工具失败、跨任务写入和并发纠正。整个生命周期采用 proposed/confirmed/superseded/invalid，冲突候选单独记录，不把两个 confirmed 值同时注入。

## 7. 单一字段归属与单摘要机制

### 7.1 Summary 只保存过程和引用

Task State 拥有已采纳目标、Todo、执行和资源状态；Facts 拥有明确参数/约束。摘要保存过程脉络、排除方向及理由、失败尝试解释、未解决讨论和下一步建议。

新 Episode 过程字段：process_notes、rejected_paths、failed_attempts、open_questions、next_step_proposals，以及 fact_refs/state_refs/source_refs。

移除重复的 key_findings、executed_actions_and_results 权威副本。没有结构化记录的历史结论可作为带来源的历史描述，但不能冒充 confirmed Fact；下一步建议也不能变成已采纳 Todo。

### 7.2 确定性去重

- Facts 按 scope+key+version 解析，Task State 按实体 ID/version 解析；引用在渲染时只展开一次。
- 摘要不得再次内联已结构化权威字段的值，使用引用。
- 过程来源按具体事件 ID/范围和 lineage 去重；不同结论引用同一消息不代表语义重复，不能直接删掉其中一个。
- 可选检索 Episode 若已在活动 manifest 或被其 lineage 覆盖，排除再次注入。
- 旧 Episode 只有粗范围时，重叠的可选 Episode 整体排除，优先当前活动视图；不引入模糊语义去重服务。

### 7.3 复用现有 Episode/Worker

沿用 memory_episodes、memory_archive_jobs 和现有 Worker，扩展版本化 Schema、生成模式与引用；不新增第二套工作摘要服务。

### T10a：机制交互评审（T11 前独立检查点）

依赖 T09/T10。先审设计转换与实际实现，再把发现转成 T11 的可复现调度用例；不必引入新框架或多 Agent。

五个机制记为 E=误差包络、Y=迟滞、C=后台 CAS、R=恢复补读、F=Facts 状态。逐项记录输入版本、事件先后/逆序、预期状态、停止条件、用户可见结果和对应测试 ID。

| 组合 | 必查交互 | 必须成立的行为 |
|---|---|---|
| E×Y | 计数转保守使 U 突增，旧 B/T 已不适用 | 重算阈值；允许紧急处置绕过冷却，不形成入队风暴 |
| E×C | 候选计数后、采用前计数模式降级 | 按当前有效计数重建，容量不合格不得仅凭 CAS 成功采用 |
| E×R | 补读返回时误差模式变保守 | 重新计算工作区，超限拒绝注入，次数不归零 |
| E×F | 事实纠正增加硬保护量 | 当前事实保留，重新分配 R；无法容纳进入恢复等待 |
| Y×C | 同来源重复触发、Job 乱序完成 | 幂等键/父版本控制，一个合法采用；过期候选不重置冷却 |
| Y×R | 恢复读取被当作新增长 | 读取重放不重复触发同来源压缩；容量紧急可绕冷却但不绕恢复次数 |
| Y×F | 冷却期间用户纠正使摘要失效 | 正确性失效立即生效，冷却不能继续发送旧事实；重建受预算限制 |
| C×R | 读取某版本来源时候选激活/来源删除 | 读取按快照校验，避免重复注入；版本冲突有界重建，不推进缺口覆盖 |
| C×F | 摘要校验后、CAS 前发生纠正 | 激活事务校验事实依赖版本或失效代次，拒绝旧候选；只检查 manifest 版本不够 |
| R×F | 读取片段含被推翻的旧值 | 历史片段标识旧版本，当前 confirmed 值优先；旧片段不能反写事实 |

至少额外检查三条三机制时序：E×C×R（计数降级+候选完成+补读返回）、C×R×F（补读中纠正且候选争用）、E×Y×F（事实增大+计数降级+冷却）。在决定性事务前后注入一次进程中断，验证重启不会重复副作用或重置恢复额度。

测试中的并发顺序通过 barrier/可控时钟/假 Worker 精确安排，不能仅靠随机 sleep。两两覆盖不等于所有组合安全；再增加带固定随机种子的事件序列测试，检查每次发送不超有效预算、事实版本有效、来源可追溯、重试有界、Thread 可接收新消息五项不变量。

产物：10 对交互评审表、三机制轨迹、未解决项和测试映射。通过标准：涉及超预算发送、旧事实采用、无限循环、重复副作用的缺陷为 0；未解决项阻止受影响能力发布，必要时维持 A/关闭自适应，而非宣称全部通过。

```python
async def recover_sources_bounded(view, epoch, profile, contract):
    while epoch.attempts_left > 0 and epoch.before_deadline():
        gate = evaluate_source_gate(contract, view)
        if gate.status == "ALLOW":
            return ready(view)
        if gate.status == "UNDETERMINED":
            break
        window = allocate_read_workspace(view, profile, epoch)
        if not window.fits_minimum_useful_slice:
            break
        ref = next_unread_dependency_range(view, epoch, window)
        if ref is None:
            break
        consume_attempt_durably_before_read(epoch, ref)  # 崩溃也不能恢复次数
        # 截止时间、单次/累计返回量都受 epoch 限制；此函数不调用压缩器。
        result = await read_range_with_deadline_and_limit(ref, window, epoch)
        persist_raw_result_and_charge_read_budget(result, epoch)
        proposal = replace_read_workspace(view, bounded_projection(result))
        if not sources_and_fact_versions_valid(proposal):
            break
        if not fits(proposal, profile):
            remember_smaller_range_for_remaining_attempt(epoch, ref)
            continue  # 不注入超限结果；最多再用剩余一次
        if not contract_missing_ids_reduced(contract, view, proposal):
            break
        view = proposal
    if evaluate_source_gate(contract, view).status == "ALLOW":
        return ready(view)
    return waiting_source(view, epoch)
```

读取失败/超时按已消耗的一次尝试处理，返回可恢复状态；不能在异常处理里递归调用此函数。若模型随后提出新的工具操作，其执行器再次检查该操作所需来源；未恢复的操作进入同一个有界策略，而不是借下一次循环刷新额度。

后台独立运行：选最小旧前缀（允许近期软保护退让）→ 校验来源 → 生成有界 Episode → 保存候选。请求边界验证依赖、重建完整视图、CAS 激活。任何失败不推进活动覆盖。

## 10. 交付边界

R1 交付限于 §1.1 的三个提交和验收，不以全部 T 任务完成为前置。R2/R3/R4 分别报告进度，未实现的 Facts、manifest、恢复、校准能力不能出现在 R1 的功能声明中。完整路线图最终才覆盖 A/B 证据、双约束、有限 G 迭代、后台与有界恢复、最小事实命令、交互评审等能力。

不承诺摘要无损、经验包络永不越界、后台追上任意突增或任意指令都能发送。应承诺有界等待、原文可恢复、权威事实不被摘要覆盖、误差和缺口可观测，以及普通历史增长不使会话永久卡死。
