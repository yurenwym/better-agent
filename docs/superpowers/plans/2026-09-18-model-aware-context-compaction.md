# 模型上下文预算修复：分期开发策略

日期：2026-09-18  
状态：待实施；本次只修订文档，未修改业务代码、运行容量探测或取得真实模型性能数据。

## 1. 本版决定

先交付预算修复，不把完整上下文治理系统当作前置条件。第一版 R1 只解决：

1. 固定 12,000 热历史预算不随模型变化。
2. 历史被提前裁剪后，才统计完整请求。
3. Profile、归档触发和最终 Gateway 的预算口径不一致。

复用现有 Episode、归档 Job、租约与事务。R1 不新建 Facts 生命周期、活动 manifest CAS 或恢复补读状态机，不实现B级估算、自适应 G，也不提前创建这些功能的空表和接口。

此前的 14 项任务移入 [完整设计参考](2026-09-18-context-compaction-design-reference.md)，保留评审结论，但不再作为 R1 的串行发布清单。本文是实施范围和顺序的权威入口，设计参考中的完整依赖图不能扩大 R1 范围。

## 2. 唯一预算契约：A 不能被绕过

### 2.1 字段和公式

| 字段 | 含义 |
|---|---|
| context_window（C） | 模型真实最大总窗口；不知道就明确表示未知，不用猜测值冒充 |
| admitted_context_limit（A） | 有证据的准入工作容量；可以低于真实窗口，不能缺省绕过 |
| soft_context_limit | 产品期望的总工作窗口上限 |
| max_output_tokens（O） | 输出预留，且不小于本次请求允许输出 |
| counter_id/version | 计数实现及固定版本 |
| counter_evidence_version | A级字节/协议上界证据、适用范围和验证报告 |
| validation_tier | A 或 B；R1 仅实现 A |

```text
S = min(soft_context_limit, A, C 若已知)
H = S - O
发送条件：完整输入预算计数 U <= H
```

包括 soft_context_limit 字段说明在内，所有地方采用同一个公式。构建器、归档器、fallback 和最终 Gateway 只调用一个 `effective_input_budget(profile)`，不得各写一份 min。

`soft_context_limit` 只是 S 的一个输入项，生效上限是 S 本身。字段名保留用于兼容，但文档与代码注释都不得把它当作生效上限，否则会再次漏掉 A。

必测边界：

- C=128K、A=64K、soft=128K：S=64K。
- C 未知、A=32K、soft=128K：S=32K。
- A 缺失、失效或没有证据：不得退化为 min(soft,C) 绕过门禁。
- H<=0 或请求输出超过 O：配置/请求校验失败，不静默调大模型能力。

K=1024；所有数值在数据库中存整数。真实容量未知时，迁移和调用方需要明确区分“真实规格未知”与“已有准入容量”，不能把未知值读成 0 或无穷大。

### 2.2 T00 两级准入，按 Profile 判断

| 等级 | 证据 | 允许的能力 |
|---|---|---|
| A 保守可用 | 端点/模型身份、单位一致的准入容量、保守计数证据、输出口径、代表性请求可发送 | R1；完成额外验证后可交付 R2 |
| B 校准可用 | A 加独立验证集误差、适用域、时延/增长样本 | R3 的估算和可选自适应优化 |

B 未完成不阻塞 A。某个 Profile 无证据只阻止它启用新发送策略，不阻止代码审计、mock、接口开发或其他已通过 A 的模型。仓库里有一个默认容量数字不算证据。

官方精确上限未知时，可以使用有证据的更小准入容量。必要时进行有预算的递增/二分探测：只将明确上下文超限作为容量拒绝，429、超时和请求体限制单独记录；保存成功范围，不必找到真实最大窗口。探测方法与停止条件见设计参考 §2.4。本次不执行付费探测。

## 3. A级到底怎么计数、收益如何判断

### 3.1 A级具体定义

复用 `backend/app/token_budget.py` 的 `Utf8UpperBoundTokenCounter.count_payload`，保持当前规范化 JSON 序列化口径，增加对未包含协议包装的明确预算：

```text
byte_bound = len(canonical_json(messages, tools).encode("utf-8"))
protocol_bound = b0 + bm * message_count + bt * tool_definition_count
                 + bc * tool_call_count + br * tool_result_count
U_A = byte_bound + protocol_bound
```

字节数是用于构造保守 Token 预算，不是真实 Token 数。该模式仅适用于已验证的文本与工具 JSON，必须验证 tokenizer 的字节上界假设及协议模板范围。

b0/bm/bt/bc/br 是适配器的非负保守包装上限，记录单位、来源和对应协议项，不能默认 0 或任意填 4096。现有 JSON 已计入的冗余结构不做激进扣减。模板存在额外项时补入协议预算。

若无法获得理论上界，只能以完整请求验证建立“经验保守模式”，必须明确标识证据强度，并限制输入类型、长度、消息/工具数量；越域复验或拒绝，出现越界就停用对应模式。没有可靠或经验保守证据的适配器不通过 A。图片/音频等另行验证，不能视为零成本。

B级才使用 `U_B=ceil(alpha*E+beta)`；R1 不依赖 alpha/beta 的拟合，也不能用 alpha=1、beta=0 冒充完成了A级验证。所有包装预算只计一次，不再额外重复扣所谓固定安全余量。

### 3.2 利用率：给可测定义，不编造预期百分比

```text
q = 服务端 actual_prompt_tokens / U_A       # 保守计数效率
f = U_A / H                                # 预算填充率
eta = 服务端 actual_prompt_tokens / H       # 真实输入利用率
eta = q * f
```

若某类输入的字节计数约为真实 Token 的 2–5 倍，且包装开销较小，填满A级预算时真实利用率约为 20%–50%。这是条件示例，不是 DeepSeek 的实测预期，也不能混同 q 与 eta。

R1 采样按中文、英文、代码、工具四类报告 q/eta 的观测区间、样本量和长度范围；样本足够才报告分位数，没有 usage 则明确未知。没有实测依据，不写统一的“预期利用率区间”。

A级上线主要收益来自取消 12,000 固定限制、完整计数和预算随模型变化，而不是高利用率。评估同一批任务的新旧原文保留量、提前归档次数、失败率、首 Token 延迟和费用。只有质量不退化且收益达到发布前约定门槛才扩大灰度；单纯 f 变高不算证明收益。

## 4. R1 只做三个提交

### M1：预算和配置契约

入口：config.py、token_budget.py、model_gateway.py、model_control.py、model_admin.py、db.py、backend/alembic/、必要的配置示例。

- [ ] 审计现有路由/配置与未提交修改；记录实际 DeepSeek 端点/模型，不输出密钥。
- [ ] 取得A级最小证据，明确 A、C、O、计数器适用域和包装预算；证据不足只暂停该 Profile 发布。
- [ ] 接入本期必要字段和不可变 Profile 版本，不预建 B/G/Facts/manifest 的框架。
- [ ] 实现唯一 S/H 计算入口、U_A 和完整消息/工具计数，返回计数模式及证据版本。
- [ ] SQLite/PostgreSQL 兼容迁移，检查旧预算及费用读取者对未知 C 的处理。
- [ ] 测 A 小于 C、C 未知、A 缺失、输出不足、格式越域及配置往返。
- [ ] 交付 A 的估计值及其证据来源（官方规格/代理配置/现有生产成功记录），并作为 **M1 的 go/no-go 判据**：R1 的主要收益是取消 12,000 固定限制，收益上限由 A 相对 12,000 的增量决定。若 A 只能取到接近 12,000 的值，先重估 R1 投入产出比，不直接进入 M2。

产物：可复用预算入口、A级证据报告（含 A 的估计值与证据强度）、迁移及配置测试。

### M2：完整请求装配与固定窗口修复

依赖：M1。

入口：conversation.py、live_model.py、memory_archive.py、transcript.py、必要的 memory_v2.py 接入和 Gateway 最终校验。

- [ ] 枚举真实 LLM 入口：对话、工具续调、规划/执行、研究、修复、摘要和 fallback，确定其实际 Profile。
- [ ] 先装配 System、当前输入、原始历史、已选记忆/Episode、Task State、Tool Call/Result 和工具 Schema，再统计完整 U_A。
- [ ] 不在完整计数前用固定 12,000 裁掉历史；动态计算历史可用空间，包装估算后仍校验完整最终请求。
- [ ] 移除 conversation.py:2611 与 conversation.py:2625 两处固定热窗口限制，取消 keep_tokens*0.8 对生产热窗口的独立触发；兼容入口不影响新主链。
- [ ] **同步定义归档保留量，不能只改触发线。** 现状 `ConversationArchiver.keep_tokens` 默认 12,000（memory_archive.py:79，startup.py:223 未覆盖），`_select_archive_prefix`（memory_archive.py:552）用它算出 `archive_count`。触发线与保留量必须来自同一个 Profile 预算：若只把触发线抬到 H 而保留量仍是 12,000，一次归档会把 12,000 以上的历史全部压掉，热窗口反而从 H 掉到 12,000，比现状更激进。
- [ ] R1 归档目标量定义为 `compact_target = ceil(compact_ratio × H)`，`compact_ratio` 由 Profile 提供（初始候选 0.7），不得在 `_select_archive_prefix` 内保留任何绝对字节常量。归档后断言 `compact_target <= 重建计数 <= H`，并断言归档后的可用历史不少于触发前的保留量。
- [ ] 保留量与触发线必须同源：Profile 未提供 `compact_ratio` 时，R1 不启用新触发线（维持现状行为），不允许出现"新触发线 + 旧保留量"的混合状态。
- [ ] 只在完整预算实际需要缩减时调用现有归档流程；复用现有完整 Turn/工具配对、租约、来源哈希、Episode 与事务，不新建状态机。
- [ ] 摘要批次按摘要模型自己的输入/输出预算配置，不能简单把所有 12,000 都替换成会话 H。
- [ ] 归档成功后重建并重新计数；失败保留原覆盖与来源，禁止偷偷丢旧历史后继续回答。
- [ ] Gateway 对最终 Payload 和实际 fallback Profile 再校验，不能复用主模型预算，也不能重放已执行工具。

产物：预算统一的调用链及归档触发。此阶段仍可能在确需归档时等待现有归档器；不宣传为后台零等待方案。

### M3：回归、收益验证与小范围发布

依赖：M2；M1/M2 各自测试随提交完成，不等到 M3 才开始测试。

- [ ] 32K/64K/较大准入容量使用相同历史，验证预算随 Profile 改变。
- [ ] 历史超过 12,000 但完整请求可容纳时，不提前裁剪或归档。
- [ ] **归档保留量回归**：构造"仅溢出少量"的场景（完整请求略超 H），断言归档后的可用历史不低于 `compact_target`，且明显高于 12,000；对同一 Profile 比较 R1 前后的原文保留量，**不得下降**。这条是 R1 的硬性验收，防止"触发线放宽、压缩力度放大"的倒退。
- [ ] 短历史加大工具 Schema、当前输入或 Memory 后，完整计数仍正确。
- [ ] 覆盖字段上限 A、fallback、摘要失败、租约失效、旧 Thread 和数据库迁移。
- [ ] 原始消息不删除，工具调用/结果完整，已归档来源保持现有可追溯能力。
- [ ] 所有实际发送请求经过统一计数；无可压缩来源的超限请求明确失败，不伪造摘要。
- [ ] 记录 q/eta、原文保留量、提前归档次数、延迟/费用；保守模式与原方案同集对比。
- [ ] 一个发布开关，小范围启用；回退不删除原文，不改运行中固定 Profile。

复用现有测试入口：test_context.py、test_transcript.py、test_model_gateway.py、test_routed_model_gateway.py、test_memory_archive.py、test_memory_conversation_flow.py、test_memory_v2.py、test_model_control.py、test_model_admin_api.py、test_startup_contract.py，以及对应数据库集成测试。仅修改和运行受本期影响的测试；真实调用需区分于 mock 结果。

R1 完成条件：预算公式不绕 A；不再由固定 12,000 决定热历史；**归档触发线与保留量同源，归档后保留量不低于 compact_target 且不低于 R1 前水平**；完整请求正确校验；归档失败不产生来源缺口；回归与收益报告可审查。

## 6. 恢复态“证据充分”判定：限定能力，不交给模型自证

本节是 R4 的设计边界，R1 不实现恢复视图。

删除泛化的 needs_source_for_next_action 授权语义。由服务端 `evaluate_source_gate(action_contract, context_snapshot)` 返回 ALLOW、NEED_SOURCE 或 UNDETERMINED，附缺失前提和原因。

| 类型 | 规则与判定者 | 允许行为 |
|---|---|---|
| 登记的结构化工具操作 | 执行服务按代码登记契约检查参数、权限、scope、状态/事实版本、来源范围及冲突 | 只放行该操作，实际执行前再次验证 |
| 精确字段读取/原文摘录 | 读取服务校验具体实体/字段与来源，使用模板或受限字段输出 | 展示读取结果，不生成额外历史推断 |
| 自由问答且有历史缺口 | 程序默认 UNDETERMINED；模型不能自报“独立/充分”改成 ALLOW | 等待相关来源、补读或要求明确任务范围，不做依赖旧历史的开放式回答 |
| 用户明确另起独立任务 | 业务层建立新作用域，保留全局权限约束，原任务仍暂停 | 作为新任务处理，不冒充原历史已恢复 |

模型可以建议操作和来源，但不能创建自己的 action_contract、删减 required_sources 或以 confidence 放行。契约未知或语义依赖未登记时返回 UNDETERMINED。

引用有效只证明来源存在，不证明任意结论成立。自然语言语义无法被上述结构检查普遍证明；这类缺口必须保留不确定性或恢复相关来源。不得将恢复机制描述为彻底消除模型幻觉。

门控绑定具体操作和上下文/事实/状态版本；发生变化重验。补读受次数/时间/空间约束，未完成来源恢复则暂停相关动作，不靠无界重试或扩大窗口解决。

## 7. 本次文档交付与非目标

本次已修正 soft_context_limit 漏 A 的公式，明确A级 U_A 和利用率评估方式，定义后续恢复判定责任，并把第一版缩为 M1–M3。另修正一处会导致行为倒退的缺口：**归档触发线与保留量必须同源**，否则触发线放宽到 H 而保留量仍为 12,000 时，一次归档会把热窗口从 H 压回 12,000（见 §4 M2 与 M3 的保留量回归验收）。

尚未实施任何业务功能，也没有真实计数/性能结果。R1 预计改善保守预算利用与提前归档问题，不承诺解决同步归档延迟、任意大当前 Turn、通用事实管理或历史缺失后的自动恢复；这些按 R2–R4 单独验收。
