## 2. 当前生产基线

- `MemoryContextProvider.select` 使用当前 query；普通对话取最新用户输入，Agent 执行路径主要取最后一次交互。
- PostgreSQL 路径：真实 embedding → pgvector cosine/HNSW 候选最多 50 条 → 最低相似度 0.35；同时做全文／trigram 召回。
- 当前排序是置顶、向量分数、词面匹配、importance 的依次优先排序，不是 RRF 融合。
- 长期记忆预算默认 1500，实际单位为 UTF-8 保守字节；命中后也可能因预算未进入上下文。
- 普通对话把可选长期记忆拼为一个整体块，最终打包时可能整块移除。
- 会话归档摘要通过覆盖边界确定性注入，不属于本次相关度召回优化范围。
- 有用户／项目／有效期隔离，以及同一 invocation 的固定快照。任何优化必须保留这些语义。

涉及文件：`backend/app/memory_v2.py`、`embedding.py`、`embedding_worker.py`、`conversation.py`、`runtime.py`、`context.py`。

## 3. 冻结评测协议

### 3.1 第一批比较什么

| 实验组 | 检索查询 | 检索与预算 | 回答模型 |
| --- | --- | --- | --- |
| A：现状 | 原始最新用户输入 | 现有 MemoryContextProvider，1500 字节 | deepseek-flash |
| B：查询补全实验 | DeepSeek 根据相同问题和近期上下文改写 | 与 A 相同，不改排序、不增预算 | 与 A 相同 |

改写提示词禁止猜测答案，只能使用当前问题和近期对话明确出现的实体。A/B 的回答端均拿到相同近期对话和原始问题，唯一受测变化是用于检索的 query，避免把“回答端多看上下文”误当成召回收益。

该原型在每题调用一次改写，以观察收益和退化；正式功能应当仅对存在指代或上下文依赖的请求启用，不直接照搬为每轮额外调用模型。

此阶段不能证明 RRF、reranker 或增大预算的效果；它们必须成为后续独立实验组。

### 3.2 数据与防止标准答案泄漏

- 所有记忆、query、history、gold、排除项、split 均已写入 JSON。
- 模型改写输入只含 `query/history`；回答输入只含 `query/history/实际注入的记忆`。
- gold 和 `answer_contains_all` 只参与本地评分，不发给模型；不让 DeepSeek 自己生成答案再给自己评分。
- A/B 使用同一语料、相同作用域、相同预算和相同回答提示词；回答调用顺序按题号交替。
- 保存数据文件、源码和脚本 SHA-256；fixture 的记忆 ID 生成固定随机种子，避免并列排序因随机 ID 改变。
- 留出题不得用于调参。本次集规模很小，是首批诊断集，不能代表生产分布，也不满足实体不相交泛化验证。

### 3.3 评分口径

| 指标 | 计算方法／用途 |
| --- | --- |
| selected Recall@5 | 每道有 gold 的题，生产 selector 返回的前 5 条命中数 / gold 数，再宏平均；不是未打包候选集的 Recall@5 |
| Injection Recall | 实際传给回答模型的条目命中数 / gold 数；仅在有 gold 的题上宏平均 |
| Precision | 每题注入条目中 gold 占比；空注入且无 gold 记 1，有 gold 记 0；报告必须写明此约定 |
| MRR | 有 gold 的题中，第一个 gold 在 selected 中的倒数排名宏平均 |
| 隔离违规 | 注入 forbidden ID 的次数；跨用户、跨项目、过期和归档命中均须单列 |
| 答案严格通过 | 包含全部指定答案片段，并引用所有必需 gold；引证必须来自实际注入集合 |
| 拒答通过 | 无证据题返回 `value=UNKNOWN` 且 `evidence_ids=[]` |
| 成本与时间 | 每次调用的 usage、耗时、请求/实际响应模型、总调用数；估算与供应商账单分开 |

脚本的答案检查是严格事实片段＋引证检查，不是完整语义质量分。合法同义表达可能被误判，必须人工复核；q16 的英语输出要求暂不计入自动分数。代码默认以简短 JSON 回复，故不能宣称评估了生产长文本对话体验。

评测脚本为记忆加了稳定 ID 引证标记，并再次在 1500 字节内打包。它同时记录 selected/injected，区分生产 selector 结果与评测提示词最终输入；它尚未走完整会话发送门，所以最终生产应用率另见 T07。

### 3.4 调用上限与失败处理

- DeepSeek：24 次改写＋48 次回答，最多 **72 次**，每次最多输出 **256 token**，输出配置上界共 18432 token；单次请求 JSON 不超过 12000 UTF-8 字节。
- `temperature=0`、thinking disabled、JSON 模式、单次 HTTP 超时 30 秒、无自动重试，DeepSeek 批次时间上限 900 秒。零温度不等于保证供应商完全确定性。
- PostgreSQL 版 embedding 最多 **70 次**：22 条文档和 A/B 各 24 条查询。沿用容器实际模型、维度和超时，不把 DeepSeek 聊天模型当 embedding 模型。
- 每次模型调用前保存请求意图，返回后保存响应 ID、实际模型字段、白名单 usage、输出和耗时。不保存认证头、数据库凭据或异常完整请求。
- 网络／格式／截断失败即停止当前 DeepSeek 批次并写 `live_incomplete`；缺失结果不记为通过。不能把部分完成的 A/B 比例当完整对比。
- 文档 embedding 不完整则停止；查询 embedding 被生产逻辑降级时保留 trace，存在服务故障降级则整体标记 `live_degraded`，不得声称真实向量验收通过。
- 当前不写未经核实的人民币／美元上限。按返回 usage 汇总实际用量，若需要金额报告，再登记当日经核实的两个供应商价格。

## 4. Docker 中的执行方式

**使用容器现有配置，但只在专用空评测库运行。**脚本不读取生产记忆、不清空生产表、不切换生产 embedding profile。

操作步骤：

1. 工具恢复后只读取服务名、数据库类型、embedding 模型/维度/端点和凭据是否存在；不要 `docker inspect` 整段输出环境变量。
2. 在相同 PostgreSQL 实例创建新的 `better_memory_eval_<batch>` 数据库，或使用独立评测实例；使用容器网络中的连接地址。数据库名必须符合脚本要求。
3. 在评测进程配置 `MEMORY_EVAL_DATABASE_URL`；不得等于应用的 `DATABASE_URL`。数据库须没有 threads 或 memory_entries 数据。
4. 在专用数据库执行当前 Alembic 迁移。仅对迁移子进程将 DATABASE_URL 指向专用库，不改变运行中应用配置。
5. 检查专用库 active embedding profile 与容器配置一致。当前 schema 的向量维度要求须被满足；不能因模型不同直接混用向量。若需修改 profile，只修改专用评测库并记录证据。
6. 将当前仓库的 backend、评测数据和可写输出目录挂载到评测进程。仅使用旧容器中的代码会评测错误版本；记录实际源码 hash。
7. 在含同一版代码的容器内运行以下命令，并保存输出。

容器内 Linux shell 示例（在当前代码的 backend 目录；前提是专用 DSN 已正确配置）：

```sh
DATABASE_URL="$MEMORY_EVAL_DATABASE_URL" python -m alembic -c alembic.ini upgrade head
python scripts/memory_recall_eval.py --postgres --execute --out ../outputs/memory-recall-v1-pg-live-01
```

宿主机无网络预检（在 backend 目录）：

```powershell
python scripts/memory_recall_eval.py --out ../outputs/memory-recall-v1-offline-new
python -m pytest tests/test_memory_recall_eval.py -q -p no:cacheprovider --basetemp=../outputs/memory-recall-tests-new
```

每次使用新的输出目录；脚本拒绝覆盖已有目录。服务名、容器 ID、数据库凭据尚未获准读取，本文件不猜测它们。Docker 镜像通常不含 docs，须挂载包含本评测目录的完整工作树。

验收：候选数量有上限；trace 不输出敏感凭据；能区分“没召回”“排得太后”“预算丢弃”。大规模结果不能冒充小样本线上延迟。

### T07 — 优化记忆预算及逐条注入

依赖：T03；与 T05 可分别测试。

涉及：`memory_v2.py`、`conversation.py`、`runtime.py`、`context.py`、预算模块。

操作：改为按实际工作窗口分配有上下限的可选记忆预算；计数单位与实际模型计数契约一致。区分稳定偏好、当前任务约束、参考事实，按条目打包，不能整块丢弃所有记忆。置顶是否必带必须明确预算失败语义。

验收：完整请求发送门内记录最终 applied IDs；保护必带归档摘要和近期对话；不通过扩大预算掩盖排序退化。设置候选召回相同、预算不同的独立消融组。

### T08 — 对齐 Agent 各阶段的查询与快照

依赖：T04、T07。

涉及：`runtime.py`、上下文 snapshot/pin。

操作：规划、执行等阶段分别使用当前目标与步骤构造查询；同一 invocation 重试保持原快照，不因新索引改变上下文。reflection 维持来源边界，不把旧记忆和摘要当新事实证据。

验收：普通对话与 Agent 阶段都有对应测试；无跨任务记忆污染；重试不多次改写、不生成不同 pin 绑定。

### T09 — 仅在评测证明需要时引入 reranker

依赖：T05、T06。

操作：检查剩余误召回是否由排序导致。若简单融合已满足目标，不增加模型调用；确需 reranker 时只处理少量候选，保持来源 ID，设置耗时上限与回退，并计入真实成本。

验收：有相同候选集下“有／无 reranker”的配对结果；收益超过延迟代价且没有隔离、无答案题回归。当前状态：可选，不能预设其必然有效。

### T10 — 扩展独立评测与人工复核

依赖：首轮 T03、T04 结果。

操作：增加不少于 100 题的新版本，覆盖短指代、多轮更正、近义表达、实体冲突、多个必要事实、无证据、预算拥挤与跨作用域；明确区分新实体留出与同实体新问法。用户真实日志须另行明确使用范围并脱敏，不默认导出。

验收：至少双人或独立复核 gold；对严格字符串规则的误判单列人工结论；保存原始自动分，不静默改分。按查询配对报告效果，不将同题重复运行当独立样本。

### T11 — 真实 A/B 验收与准入决策

依赖：T04—T08；T09 如实施则纳入。

操作：预先冻结模型、语料、参数和提示词；分别测原方案、查询补全、融合、预算、组合，先在 dev 选择，再只运行一次未使用的 holdout 决策。关键题可重复 3 次观察模型波动，但统计须按问题分组。

建议准入条件：隔离违规为 0；当前指令优先级不退化；无答案题不增加无证据回答；严格回答通过数与最终注入命中提升；延迟与费用增量可解释。具体提升门槛须在扩展基线后预注册，不能看完留出结果再定。

交付：逐题结果、完整分母、缺失/降级数量、usage、P50/P95、失败案例和回滚阈值。没有真实响应证据，不签署真实模型验收通过。

### T12 — 灰度、回滚与开发记录

依赖：T11。

操作：以独立开关分别控制查询补全、融合、预算策略；只对明确范围启用。保留原 selector 可回退，监控实际召回/注入/使用差异；发布前记录未解决项。

验收：可关闭新路径而不损坏记忆版本、pin 与确定性会话摘要；部署动作与离线实验结果分开记录。当前任务只交付评测与开发文档，不自动上线优化。
