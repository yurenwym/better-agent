# 计划交付、执行跟踪与每日复盘：工具接入及真实模型评测

日期：2026-09-20
范围：继续现有业务工具接入，不重构整个 Runtime，不新增 Agent 框架。
状态：开发任务定义、42 场景评测集与真实模型评测脚本已建立；实际结果见验收报告。

## 1. 需要解决的问题

用户要求计划、攻略或每日安排，不代表要求系统每日跟进、提醒或复盘。模型需要理解本次请求和历史中的服务意图；业务工具与程序必须保证写入范围、确认、版本和恢复规则。

当前八个目标工具已具备草稿保存、编译预览、确认激活、目标查询、今日任务、行动背景、计划读取、反馈和延期等链路能力（激活工具包含两种 mode）。本期先验证普通聊天如何进入这些能力，再补计划修改工具。

旅游不是“永不复盘”类型，健身不是“必须每日复盘”类型。每日行程、每天投入时间、每日复盘模板，都不能作为系统主动复盘的授权。

## 2. 已核实的代码边界

- `backend/app/goal_tools.py`：create_plan_draft 返回 delivery_ready=true、follow_up_enabled=false；创建文档不会直接激活执行目标。
- `backend/app/live_model.py`：Runtime 提示默认交付文档；普通聊天提示仅在明确文档请求时写入。需要消除“生成内容”和“保存文档”的表述差异。
- `backend/app/goal_reviews.py`：自动复盘入队入口为空操作，close_day 提供显式触发入口。不能声称已有周期主动复盘能力。
- `backend/app/goal_workspace.py:_phase`：无 program 时仍引导生成执行预览，需要允许文档独立交付完成。
- `LiveConversationModel.route_and_respond`：存在独立控制头、提问工具和路由适配；不能把 Registry 已注册等同于普通聊天已经可用全部业务工具。

## 3. 识别维度与执行规则

以下标签首先用于评测，不直接扩展线上协议或新增一次每轮必经的分类调用。

| 维度 | 标签 | 含义 |
| --- | --- | --- |
| tracking | none / enable / disable / clarify | 没有本次变更、请求持续服务、取消跟踪、服务意图不明确 |
| review | none / once / daily / weekly / stop / clarify | 无复盘请求、单次、每日、每周、取消、意图不明确 |
| document | answer / save / modify | 回答或非文档操作、明确保存文档、修改现有计划内容 |

tracking=enable 在此评测表示要求持续服务，包括主动周期复盘；不表示已授权 activate_goal_plan。none 可以表示维持已有服务，不等于关闭历史跟踪。标签只针对本次请求的目标，不把其他目标的偏好传播过来。

LLM 识别所需服务、提出动作和必要澄清；Harness 根据真实工具、确认和状态执行。意图已明确但缺少时间、时区等执行参数时，应补参数，不能当作没有识别到每日复盘。

单次复盘不能修改周期偏好；提醒不等于复盘；保存文档不等于激活；激活不等于主动服务授权。周期请求只能在能力实际可用并成功配置后声称已开启。

## 4. 开发任务及验收

### D1：固定意图基线与失败样例（本轮交付）

建立并运行至少 30 个真实模型场景。本轮固定 42 个案例，全部在首次调用前编写标签。不得向模型提供 expected、rationale 或场景编号。保留全部失败，不挑选成功案例重算。

### D2：打通普通聊天到已有工具

先追踪当前聊天 policy、执行物化和 Runtime 的调用路径。在现有链路上适配业务工具，复用可信身份、Registry、审批、预算和幂等，不再实现一套文档持久化。

验收链：

1. 生成攻略 → 回答交付；不创建执行目标。
2. 明确保存 → 展示写入确认（沿用现有策略）→ committed 文档及可读引用；拒绝则不写入。
3. 明确管理进度 → 获取约束 → 编译实际预览 → 用户确认具体版本 → 激活。
4. 查询今日任务和记录用户反馈 → 使用真实 ID、版本和工具结果。
5. 明确每日复盘 → 正确识别，说明或进入实际可用的配置路径；未实现调度时不得谎称已开启。

此处必须做数据库前后对比、审批拒绝、恢复重放和真实模型端到端测试。单独调用聊天适配器的本轮评测不能代替 D2 验收。

实施状态（2026-09-20）：后端链路已落地并通过确定性验收（`docs/acceptance/chat-goal-tools-d2-2026-09-20.md`）。READ 内联、WRITE 暂停审批、continuation 恢复、决定幂等、提交后落盘前恢复和 transcript 回放均有 SQLite 与 PostgreSQL 测试；真实模型端到端和页面确认卡片尚未执行。

### D3：对齐提示词、工具描述和工作台

- 生成内容不等于保存；用户明确要求创建/保存文档才执行相应写入。
- 保存成功可以结束，不默认追问是否启用每日复盘。
- 无执行目标的文档主操作为查看/修改，执行管理为可选入口。
- 已有执行预览待确认不影响文档本身可交付。
- 不以字符串关键词作为最终判断，不按领域硬编码跟踪策略。

实施状态（2026-09-20）：提示词、工具描述与页面行为已对齐；聊天页新增写入审批卡片（批准/拒绝/刷新/防重复）。D2+D3 真实模型联合验收见 `docs/acceptance/chat-goal-tools-d3-2026-09-20.md`：工具链路 6/6 通过；独立场景集全匹配 65.6% → 81.3%，仍未达本节门槛，失败全部保留。

### D4：新增修改计划文档工具

复用 PlanDocumentService 的版本写入、校验和投影流程。严格参数至少包括 document_id、expected_version_id、完整修订内容及必要标题；身份、来源和幂等键由服务端注入。

读取归属、删除状态和当前版本；事务内检查版本；经现有写入审批写入新版本并返回 hash、引用及投影状态。已有执行目标继续绑定原来源版本，不自动改写已激活行动。返回明确说明：文档变更是否尚未应用于执行安排。

验收：减少旅游景点、调整健身周安排、版本冲突、跨 owner/project 拒绝、已删除文档、拒绝审批、重放不重复版本、已激活目标不被文档修改隐式重编译。

位置：`docs/evaluation/followup-intent-v1/cases.json`。

42 个场景覆盖旅游、健身、学习、工作、生活、边界表达、跨轮变更和跨目标隔离。包括：普通攻略、每日细化、明确不跟踪、保存文档、只跟踪不复盘、每日主动复盘、每周复盘、单次复盘、提醒、复盘模板、用户自行复盘、取消、频率改口、引用模板指令和模糊委托。

每个案例含原始用户输入、必要历史、三个预期标签和必要解释。人工标签存在产品语义假设，必须公开；若发现标签有歧义，应记录争议并新建数据版本，不能在看到结果后悄悄改本轮金标。

本轮是开发基线，未保留盲测集。后续提示词修改不得只在这 42 例上宣称泛化改善；新增冻结的独立测试集或预先分组后再调优。

## 6. 两层真实模型评测

### A：结构化意图探针

通过现有 ModelGateway，将当前 conversation_instruction 与一个观测输出协议发送给真实模型。协议要求输出三个标签和理由，不提供正确答案。测试模型在明确标签契约下的理解能力。

此探针修改了输出格式，且明确了标签语义；它不是线上已有分类器，不能以探针正确率代表生产行为正确率。

### B：现有聊天适配器回放

对同一案例调用未经本轮修改的 LiveConversationModel.route_and_respond，使用生产提示词、提问工具 schema 和实际分支逻辑。记录所有模型请求、原始内容、工具选择、返回对象、协议修复、耗时及用量。

不执行工具，不启动数据库 Worker，不写入用户数据。没有实际模型调用的规则直返案例单独标记。检查回答中是否误发单次复盘问卷、是否把每日复盘当作普通建议、是否无证据声称保存/开启，以及是否混淆已有其他目标偏好。

行为结论采用逐例人工审阅记录，包含引用及理由；不能只靠“每日复盘”字符串出现与否评分。无法观察到的内部服务状态标为不可验证，不把模型承诺当作写入成功。

## 7. 指标、门槛和异常处理

- 三维全匹配率，以及 tracking、review、document 各维准确率。
- review 多分类混淆矩阵，重点区分 none、once、daily、weekly、stop。
- daily 的 TP/FP/FN、precision、recall；调用失败/格式错误计入总体分母和漏识别，不当作正确否定。
- 聊天适配器成功返回率、真实调用覆盖、截断、错误及逐例行为审阅。
- 模型调用总数、输入/缓存/输出 tokens、耗时；没有核实的计费单价时金额标未知，不填零。

后续修复验收目标：三维全匹配率至少 90%，review 至少 95%，本集 daily 误触发为零、明确 daily 请求不得漏识别；聊天行为中的未授权周期承诺为零。小样本达标不等于线上错误率为零。

本轮只测基线，不为通过门槛反复调整提示词或修改标签。失败必须给出输入、预期、实际、原始证据以及需要修改的组件。
