# DeepSeek 上下文预算最小修复开发方案

- 日期：2026-09-20
- 状态：已实施并通过配置、计量链路与真实模型 12 轮验收；见 `docs/acceptance/deepseek-context-budget-fix-2026-09-20.md`
- 目标：修复容量配置和计数单位不一致，跑通当前聊天流程
- 范围：官方 DeepSeek 接口的文本与工具调用请求

## 1. 问题与证据

当前问题不是用户输入太长，而是本地预算配置和计量链路存在缺陷。

1. `_hot_window` 曾错误地在 `gateway.control_store` 上调用 `resolved_profile()`，异常被吞掉后回退到 12,000 units。当前工作区已修正调用对象，需要保留该修复。
2. 修复后，旧 profile 仍使用 32,768 的窗口。扣除 8,192 输出预留、1,228 安全余量和 199 请求封装预留，可打包预算为 23,149。
3. 截图中的澄清续接请求已通过只读重建复现，计数为 25,408 UTF-8 字节单位。用户补充正文只有 259 字节，主要开销来自系统提示、11 个工具 schema 和澄清历史。
4. 正式回答尚未调用便被本地拒绝，不能把这一事件称作供应商确认的真实 token 超限。
5. 当前临时配置为 `DEEPSEEK_CONTEXT_WINDOW=131072`；它恢复了本例的本地预算空间，但没有修复 bytes 与 tokens 的混用。
6. profile 管理链路未完整保存容量与计数契约字段，重载后会丢失来源或退回默认计数行为。

## 2. 最小方案决策

本次只交付三个结果：

1. 官方 DeepSeek 默认使用 1,000,000 的工作窗口，并正确保存、重载和路由。
2. 所有模型容量判断使用同一个 token 估算策略，不再直接拿 UTF-8 字节数与 token 窗口比较。
3. 完成配置、全链路预算和真实澄清流程验收。

官方页面标注上下文为“1M”。本方案采用 `1_000_000` 作为保守整数工作窗口，记录官方来源及核对日期，不宣称验证了供应商的精确边界。

参考：

- [DeepSeek 官方模型说明](https://api-docs.deepseek.com/quick_start/pricing/)
- [Reasonix 默认模型窗口](https://github.com/esengine/DeepSeek-Reasonix/blob/6b93e0a/internal/config/config.go#L1874)
- [Reasonix 请求估算实现](https://github.com/esengine/DeepSeek-Reasonix/blob/6b93e0a/internal/agent/output_budget.go#L242)

## 3. 明确不纳入本次的工作

- 不接入本地精确 tokenizer。
- 不实现 usage 自动校准、容量自动学习或校准数据库。
- 不增加供应商超限后的自动压缩重试。
- 不改变业务工具权限、审批和幂等执行逻辑。
- 不做提示词重构、工具动态筛选或 schema 精简。
- 不照搬 Reasonix 的有损截断兜底。
- 不把新的估算策略标记为精确计数或已验证上界。

供应商真正返回超限时，保留现有停止行为，明确区分供应商超限与本地估算预算不足。

## 4. 开发任务

### T1：修复模型容量及计数配置的保存链路

涉及文件：

- `backend/app/model_capacity.py`
- `backend/app/config.py`
- `backend/app/model_admin.py`
- `backend/app/model_control.py`

实施要求：

1. 对官方 `api.deepseek.com` 上已识别的 DeepSeek 模型提供 1,000,000 默认工作窗口。第三方代理及未知模型不得仅凭模型名继承该值。
2. 保留用户明确配置的更小工作上限；本项目此次临时添加的 131072 覆盖，在部署验收时移除或改为新默认。
3. 修复现有容量和计数契约字段在注册、版本创建、数据库读取、路由解析中的丢失。优先使用已有字段，不另建一套 profile 系统。
4. 容量及计数策略变化必须参与版本摘要，确保修改计数方式后会生成新版本，而非复用旧版本。
5. 新估算器使用明确的 counter ID、版本和 `estimate` 模式。容量来源与计数可信度分别记录，官方窗口信息不能让估算器自动成为 `verified`。
6. 保留旧的不可变 profile。新任务使用新版本；旧任务继续绑定旧版本，不能在内部静默替换。验收须检查新任务实际选中的 profile。

完成标准：配置经过“加载 → 注册 → 数据库存储 → 重载 → 路由”后，窗口和计数策略一致。

### T2：增加简单的 token 估算器

主要文件：`backend/app/token_budget.py`。

复用现有 `TokenCounter` 接口，新增例如 `deepseek-text-estimate-v1` 的估算器，核心文本估算为：

```text
estimated_tokens(text) = ceil(len(text.encode("utf-8")) / 4)
```

实施要求：

1. 明确标记为启发式估算。这个公式可能低估，不是数学意义上的安全上界。
2. 覆盖实际发给模型的系统提示、消息、工具定义、工具调用参数和工具结果，不能只计算用户正文。
3. 复用现有请求构造及封装开销预留机制，并用新计数器重新计算开销，避免复制两套请求构造逻辑。
4. 输入预算继续扣除本次输出预留及现有安全余量；本次不引入新的动态输出裁减机制。
5. 不全局替换 `DEFAULT_TOKEN_COUNTER`，避免改变存储限额、摘要长度限制及旧档案的版本语义。为目标路由显式选择新策略。
6. 已有严格计数模式维持其证据要求，新估算器不能通过伪造验证标记进入严格模式。

本次不追求准确率承诺。验收要记录估算值与真实 usage 的差异，不能声称“估算一定大于实际 token”。

### T3：统一所有容量判断入口

这是本次修复的核心。只增加估算器、只改 profile 或只改前置检查，都不算完成。

| 位置 | 修改要求 |
| --- | --- |
| `conversation.py::_hot_window` | 从实际路由 profile 取得窗口与计数策略；有路由但解析失败时明确报配置错误，不能吞错后静默回到 12k |
| `conversation.py::_archive_history_before_generation` | 移除模型预算测量中的硬编码 `DEFAULT_TOKEN_COUNTER`，使用目标 profile 的估算器 |
| `live_model.py` 的请求打包 | 预检与发送使用一致的计数策略、工具集合和输出预留 |
| `model_control.py` 的路由校验 | 每个候选 profile 使用自己的窗口和计数策略，不能给 fallback 套主模型预算 |
| `model_gateway.py` 的单模型校验 | 使用实际发送 profile 对应的估算器 |
| `assert_provider_payload_fits` | 最终请求体仍做检查，但不得重新以原始字节数对比 token 窗口 |
| `memory_archive.py`、`transcript.py`、`memory_v2.py` | 审核与模型窗口直接比较的数值并统一单位；纯字节长度限制保持 bytes |

同一次发送固定使用一份计数配置。预检按标准请求形状计量，最终校验按适配后的请求形状计量，二者差异通过封装预留覆盖；不要求两个数值机械相等。

工具循环追加结果后必须重新计量。不得以首次请求已通过为由跳过后续检查。

`context.counted` 等诊断至少能追踪：

- 实际 profile 版本和工作窗口。
- counter ID、版本及 `estimate` 模式。
- 估算输入 token、输出预留和有效输入预算。
- 原始 payload 字节数（如记录），明确字段名和单位，不再混称 token。

## 5. 实施顺序

1. 建立故障回归夹具：保留系统提示、11 个工具、澄清调用和结果的结构，确保改动前能够暴露问题。真实用户内容不得未经处理提交到仓库。
2. 完成 T1，验证配置存取及实际路由版本。
3. 完成 T2 和 T3，全链路接入后再执行预算边界测试，不能在中间状态宣布修复。
4. 修复与本次容量及计数改动相关的失败测试，不能删除或弱化断言掩盖字段丢失。
5. 完成目标单元测试和模拟传输集成测试。
6. 部署新配置并执行真实模型验收，记录结果。

本次文档编写不执行第 6 步。后续开发时，真实模型调用和服务重启按届时用户授权范围执行。

## 6. 验收清单

### A. 配置和持久化

- [ ] 官方 DeepSeek 无手动覆盖时，工作窗口为 1,000,000。
- [ ] 手动较小上限生效，第三方同名模型不误用官方默认。
- [ ] profile 注册、重载和路由后，窗口、counter ID、版本、模式及来源不丢失。
- [ ] counter 变化会生成新 profile 版本；新任务实际选中新版本。
- [ ] 有路由但 profile 解析失败，不再静默使用 12k。

### B. 计量链路

- [ ] 在受控的 32k profile 下，“原始字节数超过输入预算、估算 token 未超预算”的请求通过最终模拟传输校验。这证明修复不只是靠 1M 掩盖错误。
- [ ] 估算 token 确实超过预算的请求仍被正确处理，不允许无条件放行。
- [ ] conversation 预检、打包、路由、单模型网关与最终 payload 校验使用目标 profile 对应的策略。
- [ ] 中文、英文、混合文本和工具参数均有覆盖。
- [ ] 11 个工具定义及澄清历史均参与计数，没有通过删工具或漏计历史让测试通过。
- [ ] fallback 和工具循环新增结果重新计量。
- [ ] 文件、工具结果等 bytes 限制未被错误地缩小为原来的四分之一。
- [ ] 现有严格计数模式没有被新估算器冒充或绕过。

### C. 故障回归和真实模型

- [ ] 重放原先约 25,408 字节的澄清请求，不再发生 bytes 与 tokens 混用导致的拒绝。
- [ ] 新建任务跑通“你好 → 桂林七天计划 → 澄清补充 → 完整回答”。
- [ ] 执行一次受控长输入请求，不要求填满 1M 窗口。
- [ ] 保存本次请求的估算输入 token、供应商实际输入 token、工作窗口和结果；缓存命中的输入也计入实际上下文用量。
- [ ] 真正的供应商超限仍然停止，不原样无限重试，不重复业务写入。
- [ ] readiness 只作为配置检查，不能代替真实请求验收。

已知此前相关检查出现 61 项通过、9 项失败，失败集中在容量管理链路。本次须复查并修复涉及本方案的失败；若仍有遗留失败，交付报告逐项说明，不能报告为“相关测试全部通过”。

## 7. 交付物与完成定义

交付内容：

1. 容量存取修复、简单估算器及全链路接入代码。
2. 故障回归、持久化和最终发送边界测试。
3. `.env.example` / README 中对官方默认窗口、手动覆盖和估算模式的说明。
4. 一份验收记录，列出通过与失败项、实际请求计数及尚存限制。

只有“配置不丢失、所有容量判断单位一致、最终发送不再退回字节拦截、真实澄清流程成功”同时成立，才能认定本次问题解决。

保留的限制：固定比例估算可能低估特殊文本。后续若真实数据表明误差频繁影响使用，再单独引入 usage 校准或经过验证的 tokenizer，不预先扩大本次范围。
