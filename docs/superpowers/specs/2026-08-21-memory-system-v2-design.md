# 个人 Agent 记忆系统重构设计：简洁分层与持续记忆

> 状态：设计提案
>
> 日期：2026-08-21
>
> 适用分支：`codex/personal-agent-v1`
>
> 目标：在保留现有 SQLite 事务、用户确认、版本审计和执行恢复能力的前提下，采用类似 Nanobot 的清晰记忆分层，消除当前“记忆、计划、轨迹、Checkpoint 混在一起”的理解成本。

## 1. 结论

当前系统已经有记忆能力，但它更像多个可靠模块的集合，而不是一套用户容易理解的记忆模型。主要问题不是缺少 `MemoryService`，而是缺少一个明确的中间层：

```text
当前对话  →  压缩后的经历摘要  →  长期知识
```

本设计采用四个相互隔离的层次：

1. **短期记忆（Short-term Memory）**：当前 Thread 中的最近对话。
2. **经历摘要（Episodic Archive）**：对较早对话的压缩记录，描述“发生过什么”。
3. **长期知识（Semantic Memory）**：经过整理、确认后仍然值得保留的用户偏好、事实和项目知识。
4. **执行账本（Execution Ledger）**：Plan、Event、Checkpoint、Stats 等可靠性数据。它们不是用户记忆，不进入长期记忆目录。

最终用户只需要理解两类内容：

- “最近我们聊了什么”：短期记忆和经历摘要；
- “Agent 长期知道什么”：长期知识。

执行账本继续服务于恢复、审计和轨迹展示，但不再与用户记忆混称。

## 2. 背景

Better Agent 的产品目标不是一次性回答问题，而是持续帮助用户完成目标、调整计划并逐步成为更好的自己。因此系统需要保留跨轮次、跨任务的有效信息，例如：

- 用户更喜欢简短还是详细的计划；
- 用户每周可用的训练时间；
- 用户的长期训练目标和限制条件；
- 某个项目已经做过哪些决策；
- 某个计划当前处于什么版本。

最初的 V1 设计优先保证了执行可靠性：显式状态机、计划版本、工具审批、Checkpoint、事件轨迹和 Markdown 记忆都已经存在。后续又加入了 Conversation Runtime、Ask 工具、计划文档持久化和渲染编辑器。

这些能力解决了“能不能可靠执行”的问题，但没有形成足够直观的“Agent 到底记住了什么、为什么使用这些信息”的产品模型。

本设计参考 Nanobot 当前公开的记忆设计。Nanobot 将记忆拆为当前会话、`memory/history.jsonl` 压缩历史、`SOUL.md` / `USER.md` / `memory/MEMORY.md` 长期知识，并用 Consolidator 和 Dream 逐步整理记忆：

- [Nanobot memory design](https://github.com/HKUDS/nanobot/blob/main/docs/memory.md)
- [Nanobot MemoryStore](https://github.com/HKUDS/nanobot/blob/main/nanobot/agent/memory.py)
- [Nanobot ContextBuilder](https://github.com/HKUDS/nanobot/blob/main/nanobot/agent/context.py)

本项目不直接复制 Nanobot 的文件实现，而是吸收其“分层、可见、渐进整理”的设计原则，并保留本项目对事务、审批和执行恢复的要求。

## 3. 当前系统诊断

### 3.1 当前已有的短期记忆

Conversation Runtime 将对话持久化到 SQLite：

- `threads`：一条连续对话；
- `turns`：每次用户提交；
- `thread_messages`：用户和模型消息；
- `thread_events`：对话状态和流式事件。

它能支持刷新恢复、流式消息、Ask 继续回答和断线重连。当前对话历史是普通聊天的主要上下文来源。

但是，当前没有独立的“旧对话压缩摘要”层。历史消息要么继续作为对话历史参与组装，要么在上下文超限时被裁剪；它们不会自动沉淀为可持续复用的经历摘要。

### 3.2 当前已有的工作记忆

`ContextAssembler` 在每次 Agent 模型调用前临时组装上下文，内容包括：

- 当前用户指令；
- Goal；
- 当前 PlanVersion 和 PlanStep；
- 当前 Skill；
- 最近交互历史；
- 工具结果；
- 已确认的长期记忆。

它会做长度裁剪并生成 `ContextSnapshot` 和 Hash。这个层次是一次模型调用的工作区，不应该被当作长期记忆。

### 3.3 当前已有的长期记忆

当前 `MemoryService` 的流程是：

```text
Agent 复盘
  → LLM 返回 preference / habit 候选
  → 写入 SQLite memory_candidates，状态为 proposed
  → 用户确认、拒绝或编辑
  → 确认后写入 Markdown 文件
  → 后续 Agent 执行时读取
  → 记录 memory.applied
```

当前文件结构为：

```text
data/memory/
├── preferences.md
├── projects/<project_id>.md
├── skills/<skill_name>.md
└── .versions/
```

这套设计有明显优点：

- 长期记忆不会被模型静默写入；
- 用户可以确认、拒绝、编辑、停用和回滚；
- 有 Markdown 可读文件和 SQLite 版本记录；
- 有 `global`、`project`、`skill` 作用域；
- 记忆进入执行上下文时会产生 `memory.applied` 事件。

### 3.4 当前不存在真正的摘要层

当前 LLM 复盘主要负责提取长期记忆候选，并不负责把旧对话压缩成独立的经历摘要。因此当前系统缺少类似 Nanobot `history.jsonl` 的结构：

```text
某次训练计划讨论发生过什么？
某次旅行计划做过哪些取舍？
某个目标为什么被调整？
```

这些信息现在主要分散在对话消息、计划文档和事件轨迹中，不能以低成本、稳定方式参与后续上下文。

### 3.5 Plan、Event、Checkpoint 不是长期记忆

当前系统中的以下数据应该保留，但不应归入用户记忆：

- `PlanDocument` / `PlanDocumentVersion`：用户维护的计划文档；
- `PlanVersion`：一次执行使用的结构化计划快照；
- `EventStore`：执行和审计事件；
- `CheckpointStore`：恢复所需的状态；
- `StatsProjector`：从事件重建的统计数据。

它们是**执行账本和用户资产**，而不是“Agent 对用户的长期认识”。将它们都称为记忆会导致架构和 UI 都变复杂。

## 4. 当前问题

### 4.1 记忆概念边界混乱

用户很难区分：

- 我刚才说的话；
- Agent 对旧对话的总结；
- Agent 对我的长期认识；
- 某个计划的内容；
- 某次执行的事件和恢复信息。

这些数据在代码中有不同模块，但在产品层没有形成清晰的记忆语言。

### 4.2 缺少“对话 → 摘要 → 长期知识”的中间过程

当前长期记忆只在 Agent Run 复盘阶段产生候选。普通聊天中的重要信息不会自然进入一个可检索、可整理的经历摘要层。

结果是：

- 对话很长时只能裁剪；
- 旧决策不容易被后续对话复用；
- 用户感觉 Agent 要么“什么都记住”，要么“什么都不记得”。

### 4.3 长期记忆对普通聊天的接入不统一

已确认记忆主要接入 Agent Runtime 的执行上下文。普通 Conversation Runtime 更依赖当前 Thread 历史和活动计划上下文，尚未形成统一规则：

```text
普通回答：最近对话 + 适量长期知识
计划执行：当前计划 + 项目知识 + 用户偏好
```

这会导致同一条已确认记忆在不同入口的可见性不一致。

### 4.4 缺少长期记忆维护策略

当前已有确认、编辑、停用和回滚，但还缺少：

- 相同记忆的去重；
- 新旧偏好冲突处理；
- 过时记忆的更新建议；
- 摘要和长期知识的定期整理；
- 用户能够理解的“为什么保留/为什么更新”说明。

### 4.5 记忆逻辑分散

存储、候选生成、作用域筛选、上下文应用和 UI 操作分散在多个模块中。缺少一个明确的记忆策略层，导致以后继续增加“自动记忆”“临时记忆”“项目记忆”时容易继续堆概念。

## 5. 目标与非目标

### 5.1 目标

1. 让用户能用一句话理解记忆系统。
2. 明确区分短期对话、经历摘要、长期知识和执行账本。
3. 让旧对话可以被压缩保存，而不是只能裁剪或永久保留原文。
4. 让长期知识可读、可审查、可修改、可恢复。
5. 让普通聊天和 Agent 执行使用一致的长期知识规则。
6. 保留用户确认机制，避免模型静默改变长期用户画像。
7. 不引入 RAG、向量数据库、Redis、后台分布式任务或多 Agent。

### 5.2 非目标

- 不做语义向量检索；
- 不把所有事件日志转成自然语言记忆；
- 不展示模型隐藏思维链；
- 不复制 Nanobot 的 Git 工作树作为本项目运行时依赖；
- 不在本阶段自动删除历史数据；
- 不允许模型直接修改计划、记忆和数据库。

## 6. 优化后的记忆模型

### 6.1 四层模型

```text
┌──────────────────────────────────────────────┐
│ 1. 短期记忆 Short-term                       │
│ 当前 Thread 最近消息                         │
└──────────────────────────────────────────────┘
                       │ 超过上下文阈值
                       ▼
┌──────────────────────────────────────────────┐
│ 2. 经历摘要 Episodic Archive                 │
│ history.jsonl：发生过什么、做过什么决定       │
└──────────────────────────────────────────────┘
                       │ Dream / Consolidator
                       ▼
┌──────────────────────────────────────────────┐
│ 3. 长期知识 Semantic Memory                  │
│ USER.md、MEMORY.md、projects/*.md            │
│ 用户偏好、稳定事实、项目知识                  │
└──────────────────────────────────────────────┘

┌──────────────────────────────────────────────┐
│ 4. 执行账本 Execution Ledger                  │
│ Plan / Event / Checkpoint / Stats             │
│ 只服务于执行、恢复、审计和展示                 │
└──────────────────────────────────────────────┘
```

前三层是记忆，第四层是可靠性基础设施。第四层不会被整体注入模型上下文。

### 6.2 短期记忆：当前对话窗口

短期记忆保存当前 Thread 的最近消息，不追求永久保留全部内容进入模型上下文。

建议默认策略：

- 最近最多 50 条消息；
- 最近历史最多 8,000 Token；
- 当前用户消息永远保留；
- 当前活动计划上下文单独固定保留；
- 超出阈值时先归档摘要，再裁剪旧消息。

短期记忆的职责只有一个：帮助模型理解当前正在进行的对话。

### 6.3 经历摘要：`history.jsonl`

新增一个面向机器读取、也可被用户查看的追加式经历摘要文件：

```text
data/memory/history.jsonl
```

每行代表一段已经压缩的经历：

```json
{
  "cursor": 42,
  "timestamp": "2026-08-21T10:30:00+08:00",
  "thread_id": "thread_xxx",
  "turn_range": [12, 18],
  "content": "用户决定将训练安排调整为每周三次，周末进行长距离骑行。",
  "topics": ["骑行训练", "时间安排"]
}
```

约束：

- 追加写入，不覆盖旧摘要；
- 使用 cursor 标记已归档范围；
- 摘要失败时保留安全的原文引用，不丢失事实；
- 摘要不是长期用户画像，不需要逐条用户确认；
- 摘要不允许修改工具权限、计划审批或安全策略。

归档触发条件：

1. 最近消息超过数量或 Token 阈值；
2. 一个自然任务或计划阶段完成；
3. 用户主动要求“总结这段对话”；
4. 应用启动恢复时发现存在未归档的旧消息。

### 6.4 长期知识：三个清晰文件

长期知识采用 Nanobot 风格的文件语义，但保留本项目的 SQLite 版本账本：

```text
data/memory/
├── USER.md                    # 用户稳定偏好、习惯和长期约束
├── MEMORY.md                  # 跨任务稳定事实、重要决策和经验
├── projects/
│   └── <project_id>.md        # 某个项目或领域的知识
├── history.jsonl              # 经历摘要
├── .cursor                    # 短期消息归档游标
└── .consolidator_cursor       # 长期知识整理游标
```

文件职责：

| 文件 | 保存内容 | 示例 |
|---|---|---|
| `USER.md` | 用户长期偏好和习惯 | 偏好简洁计划、每周只能训练三天 |
| `MEMORY.md` | 跨任务稳定事实和重要决策 | 已决定优先完成骑行基础训练 |
| `projects/*.md` | 某个项目的事实和约束 | Better Agent 的架构取舍 |
| `history.jsonl` | 发生过什么 | 某次对话做过的计划调整 |

`skill` 不再作为用户需要理解的一级长期记忆类型。现有 `skills/*.md` 记录可以在迁移期保留，但新的长期记忆默认归入 `USER.md`、`MEMORY.md` 或项目文件。Skill 可以读取相关知识，但不应拥有一套用户难以发现的独立画像。

### 6.5 执行账本保持独立

以下数据继续保存在 SQLite 和事件系统中：

- PlanDocument / PlanVersion；
- Event / ThreadEvent；
- Checkpoint；
- Approval；
- ToolCall；
- StatsProjector 结果。

它们可在轨迹页和计划页展示，但不写入 `MEMORY.md`，也不作为长期用户知识自动注入模型。

## 7. 整理机制：Consolidator 与 Dream

### 7.1 Consolidator：只负责压缩经历

Consolidator 接收一段已经完成或过长的 Thread 消息，输出简短经历摘要并追加到 `history.jsonl`。

Consolidator 不负责：

- 修改长期用户画像；
- 修改计划；
- 调用 WRITE 工具；
- 直接改变执行状态。

这样可以让“保存发生过什么”和“判断什么值得长期保留”分开。

### 7.2 Dream：整理长期知识

Dream 是低频的长期记忆整理动作，可以由以下方式触发：

- 用户在记忆页面手动触发；
- 一段对话完成且出现新的经历摘要；
- 应用空闲或启动恢复时；
- 后续再增加本地定时触发。

Dream 读取：

- 新的 `history.jsonl` 条目；
- 当前 `USER.md`；
- 当前 `MEMORY.md`；
- 对应项目文件。

Dream 输出的是结构化变更候选，而不是直接静默覆盖文件：

```json
{
  "operation": "add | update | archive | no_change",
  "target": "USER.md",
  "content": "用户偏好简洁、可执行的计划",
  "reason": "来自最近三次对话的一致表达",
  "evidence": ["history:42", "history:47"],
  "confidence": 0.91
}
```

默认策略：

- 经历摘要可以自动追加；
- 长期知识新增、更新和归档默认需要用户确认；
- 用户确认后才提交 Markdown 正式版本；
- 每次提交保留 SQLite 版本、Hash、来源和事件。

这比 Nanobot 更保守，但更符合本项目“用户掌控长期状态”的安全边界。

## 8. 上下文注入策略

### 8.1 普通聊天

普通回答使用：

```text
系统规则
+ 当前 Thread 最近消息
+ 最近若干条经历摘要
+ USER.md
+ MEMORY.md
+ 当前项目文件（如果存在）
+ 当前活动计划（如果存在）
```

不读取完整 Event、Checkpoint、Stats，也不把所有旧对话原文塞进模型。

### 8.2 Agent 执行

Agent 执行使用：

```text
系统规则
+ 当前用户指令
+ 当前 Goal
+ 固定引用的 PlanVersion
+ 当前 PlanStep
+ 相关项目知识
+ 用户偏好
+ 必要的经历摘要
+ 工具结果
```

每次模型调用仍然生成 `ContextSnapshot` 和 Hash，保证可审计和可复现。

### 8.3 不做 RAG

本方案不使用向量数据库。记忆选择规则保持简单：

1. 当前用户消息和当前计划优先；
2. 当前项目知识优先于全局知识；
3. 用户偏好作为稳定约束；
4. 经历摘要只取最近和与当前项目相关的有限条目；
5. 超出预算时按优先级裁剪。

如果未来摘要规模增长到无法通过显式作用域和有限窗口管理，再单独评估检索方案。

## 9. 用户交互设计

记忆页面不再把所有内容混为“记忆记录”，而是分为三个区域：

### 最近经历

展示 `history.jsonl` 中的摘要，说明：

- 发生时间；
- 来源对话；
- 摘要内容；
- 是否已经被长期知识吸收。

### 我的长期偏好

展示 `USER.md` 的结构化条目：

- 待确认；
- 已确认；
- 已停用；
- 版本和来源。

### 项目知识

展示当前项目的 `projects/<project_id>.md`，支持查看、编辑和回滚。

轨迹页只展示：

- `context.snapshot_created`；
- `memory.applied`；
- `memory.candidate_created`；
- `memory.confirmed`；
- `memory.updated`；

用户可以看到“本次回答使用了哪些长期知识”，但不需要查看原始 JSON 事件。

## 10. 现有数据迁移

| 当前数据 | 目标位置 | 迁移策略 |
|---|---|---|
| `preferences.md` | `USER.md` | 保留内容，建立新版本记录 |
| `projects/<id>.md` | `projects/<id>.md` | 直接保留 |
| `skills/<name>.md` | `USER.md` / `MEMORY.md` / 项目文件 | 按内容归类，迁移期兼容读取 |
| `memory_candidates` | SQLite 元数据 | 保留候选、状态、证据和 Hash |
| `memory_file_versions` | SQLite 版本账本 | 继续作为恢复和审计依据 |
| `thread_messages` | 短期记忆来源 | 不迁移，增加归档游标 |
| `events` / `checkpoints` | 执行账本 | 不迁移到长期记忆 |
| `PlanDocument` | 计划资产 | 不迁移到长期记忆 |

历史对话不要求一次性全部重写。首次运行时可以只从最近一个活动 Thread 开始归档，后续按阈值增量处理。

## 11. 模块职责

| 模块 | 新职责 |
|---|---|
| `ConversationService` | 保存短期对话和归档边界 |
| `ConversationArchiveService` | 生成并追加经历摘要 |
| `SemanticMemoryService` | 管理长期知识候选、确认、版本和冲突 |
| `MemoryConsolidator` | 从经历摘要生成长期知识变更候选 |
| `ContextAssembler` | 只负责按策略读取和组装上下文，不写记忆 |
| `AgentRuntime` | 使用长期知识，不负责定义长期知识 |
| `PlanDocumentService` | 管理计划文档，不归入记忆 |
| `EventStore` / `CheckpointStore` | 执行账本和恢复，不归入记忆 |
| `MemoryPage` | 展示最近经历、长期偏好和项目知识 |

核心原则是：**读取上下文和修改记忆分离**。`ContextAssembler` 只能读，`MemoryConsolidator` 才能提出修改，正式写入必须经过确认和版本提交。

## 12. 实施阶段

### 阶段 0：先建立统一术语和契约

- 新增本设计文档；
- 明确 Memory、Archive、Plan、Event、Checkpoint 的边界；
- 为事件增加统一的 memory source/version 字段；
- 不改现有用户数据。

### 阶段 1：经历摘要层

- 新增 `history.jsonl` 和 cursor；
- 实现基于消息数量/Token 阈值的归档；
- 实现摘要失败时的安全降级；
- 在上下文中使用有限的经历摘要；
- 添加重启、重复归档和 cursor 连续性测试。

### 阶段 2：长期知识整理层

- 将现有 `MemoryService` 收敛为 `SemanticMemoryService`；
- 将长期文件统一为 `USER.md`、`MEMORY.md` 和项目文件；
- 增加 Dream/Consolidator 的结构化变更候选；
- 增加去重、冲突、归档和证据关联；
- 保留用户确认和版本回滚。

### 阶段 3：统一上下文和 UI

- 普通聊天接入确认后的长期知识；
- Agent 执行继续使用计划和项目上下文；
- 轨迹中显示使用的记忆版本；
- 记忆页面按“最近经历 / 我的偏好 / 项目知识”分区。

### 阶段 4：验收和真实模型测试

- 用确定性模型验证记忆边界；
- 使用指定 `LLM_AP.txt` 验证真实模型的摘要和长期知识候选质量；
- 检查脱敏导出不包含 Key 和敏感原文；
- 检查用户拒绝的记忆不会进入后续上下文。

## 13. 验收标准

### 分层正确性

- 当前消息只进入短期 Thread 历史；
- 旧消息能够生成经历摘要；
- 经历摘要不会自动变成长期用户偏好；
- 长期知识必须有明确来源和版本；
- Plan、Event、Checkpoint 不会被误写入长期记忆。

### 长期知识安全

- 用户未确认的候选不会进入普通回答或 Agent 执行上下文；
- 用户拒绝后不会再次被自动应用；
- 更新长期知识会产生新版本，不覆盖历史；
- 冲突内容会生成待确认变更，不静默覆盖；
- 记忆文件损坏或外部修改时保留冲突状态并可恢复。

### 上下文质量

- 普通聊天能够读取确认后的 `USER.md` / `MEMORY.md`；
- Agent 执行能够读取与当前项目相关的知识；
- 上下文超过预算时优先保留当前指令、计划和用户偏好；
- 每次使用记忆都能在轨迹中看到对应版本；
- 不使用向量检索也能通过作用域和摘要窗口得到稳定结果。

### 用户可理解性

- 用户能在页面上区分最近经历和长期知识；
- 用户能看到记忆来源、状态和影响范围；
- 用户能确认、编辑、停用、恢复长期知识；
- 页面不要求用户阅读原始事件 JSON 才能理解 Agent 的行为。

## 14. 最终判断

Nanobot 值得借鉴的不是某个文件名，而是它对记忆职责的划分：

```text
session.messages  = 现在正在发生什么
history.jsonl     = 过去发生过什么
USER/MEMORY.md    = 什么值得长期记住
Git / SQLite      = 这些内容如何被审计和恢复
```

Better Agent 的最终方案应采用同样清晰的心智模型，同时保留自己的安全边界：

- 摘要可以自动生成；
- 长期知识默认需要用户确认；
- 计划和执行账本独立管理；
- SQLite 负责事务、版本和恢复；
- Markdown 负责可读、可编辑的长期内容；
- 不引入 RAG 或额外基础设施来掩盖记忆边界问题。

这会让记忆系统从“多个模块都在保存一些东西”变成一条用户可以理解的连续链路：

```text
对话 → 摘要 → 长期知识 → 上下文使用 → 用户确认与修正
```
