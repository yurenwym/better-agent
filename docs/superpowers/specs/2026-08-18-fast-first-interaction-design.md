# 快速首响应与意图路由设计

> 状态：待评审方案，尚未实现
>
> 日期：2026-08-18

## 1. 用户问题

用户反馈当前 Agent 流程过慢：用户发送一句话后，系统会先进行澄清、生成完整计划、等待审批，甚至开始执行，用户需要长时间等待模型返回结果。截图中，用户只是输入“给我一个学习 python 脚本的计划”，系统已经生成了完整的 7 步、4～6 周计划，并进入“计划已经准备好”的审批阶段，用户在完整结果出现前缺少即时反馈和决策权。

用户希望解决以下问题：

1. 是否应该在代码层面约束流程，避免所有问题都进入完整 Agent 执行链路。
2. 是否应该由 LLM 判断用户的问题属于目标、攻略、长期任务还是普通问题。
3. 对目标、攻略或长期类型的问题，第一步先给出简短方案，让用户选择“继续”还是“修改”。
4. 对非目标类问题，应该直接回答，而不是让用户等待计划生成。
5. 用户应该尽快看到第一条有用结果，而不是一直等待完整执行结束。

## 2. 目标与非目标

### 2.1 目标

- 用户发送后立即看到消息已接收和当前处理阶段。
- 目标、攻略和长期任务先得到可读的简短预览。
- 用户确认后才生成完整计划、调用工具或进入 ReAct。
- 普通问题直接流式回答，不进入计划审批链路。
- 信息不足时给出合理假设，并只提出一个关键问题，不显示空白等待状态。
- 取消操作始终可见，流式模型响应可以被中断。
- 保留现有显式状态机、SQLite、SSE、轨迹和审计能力。

### 2.2 非目标

- 不引入 RAG、多 Agent、MCP、Shell、Redis、Celery、微服务或工具并行。
- 不引入跨厂商静默 fallback。
- 不让 LLM 直接改变运行状态、绕过审批或决定安全边界。
- 不在用户确认前生成完整、昂贵或可能产生副作用的执行计划。

## 3. 方案比较

### 方案 A：纯代码规则

根据关键词、句式、长度和是否包含时间范围判断请求类型。

- 优点：速度快、成本低、行为容易测试。
- 缺点：语义判断脆弱，容易把“攻略”误判为普通问题，也难以识别隐含的长期目标。

### 方案 B：独立 LLM 分类器

每次消息先调用一次 LLM 分类，再调用另一次 LLM 生成答案或计划。

- 优点：语义判断灵活。
- 缺点：额外增加一次模型往返，可能让当前等待问题更严重；分类器的结果还需要代码校验。

### 方案 C：轻量路由与代码硬约束结合（推荐）

将现有的“是否需要澄清”调用升级为一次轻量路由调用，同时返回请求类型和第一版简短预览。LLM 负责语义判断，Runtime 负责校验结果和约束后续动作。

该方案不增加一次独立的 LLM 请求，且能复用现有模型网关、SSE、事件日志和状态机。

## 4. 推荐交互流程

```text
用户发送消息
    ↓
立即显示“已收到，正在理解请求”
    ↓
一次轻量 LLM 路由：判断类型 + 生成第一版响应
    ↓
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 目标类       │ 攻略类       │ 长期类       │ 普通问题     │
│ 简短方案     │ 精简攻略     │ 阶段预览     │ 直接回答     │
│ 继续/修改    │ 展开/调整    │ 继续/修改    │ 可选转目标   │
└──────────────┴──────────────┴──────────────┴──────────────┘
    ↓
只有用户选择继续或展开后，才进入完整计划、工具和执行流程
```

### 4.1 路由结果

路由调用使用小输出预算和严格结构化结果，建议包含：

```json
{
  "mode": "goal | guide | long_term | direct | clarify",
  "confidence": 0.92,
  "preview": "给用户看的第一版简短结果",
  "assumptions": ["默认每周学习 3～5 小时"],
  "needs_user_choice": true,
  "choice_kind": "continue_modify"
}
```

Runtime 必须校验：未知 `mode`、缺少 `preview`、非法按钮类型或超出长度限制时，统一降级为安全的直接回答或简短澄清，不能让异常 JSON 进入状态机。

### 4.2 不同类型的行为

| 类型 | 第一响应 | 用户操作 | 后续行为 |
|---|---|---|---|
| `goal` 目标类 | 3～5 条可执行方向、假设、预计步骤 | 继续执行 / 修改方案 | 确认后生成完整计划 |
| `guide` 攻略类 | 先给精简版攻略和关键提醒 | 展开详细攻略 / 调整偏好 | 选择后生成扩展内容 |
| `long_term` 长期类 | 给出阶段、周期和第一步行动 | 继续执行 / 修改周期 | 确认后进入长期计划 |
| `direct` 普通问题 | 直接流式回答 | 可选转为目标 | 不生成计划、不显示审批 |
| `clarify` 信息不足 | 先给合理假设，再问一个关键问题 | 补充信息 / 采用默认方案 | 进入对应类型流程 |

## 5. 状态机建议

建议新增显式状态 `AWAITING_DIRECTION`，用于表示“简短方案已经给出，正在等待用户选择”。这样可以与完整计划审批区分开。

```text
RECEIVED / CLARIFYING
        ↓
AWAITING_DIRECTION
   ┌────┴────┐
继续执行   修改方案
   ↓          ↓
PLANNING   CLARIFYING
   ↓
AWAITING_APPROVAL
   ↓
EXECUTING
```

`direct` 模式不进入 `PLANNING`、`AWAITING_APPROVAL` 或 `EXECUTING`。它只记录当前交互和模型回答；用户明确选择“转为目标”后，才创建或切换到目标执行流程。

如果实现阶段为了兼容现有状态机暂时不增加状态，也必须至少持久化 `interaction_mode=preview` 和 `preview_status=awaiting_direction`，不能把简短预览伪装成已批准的完整计划。

## 6. 代码层面的硬约束

预览阶段禁止：

- 创建完整 `PlanVersion`。
- 消耗 ReAct 轮数或执行预算。
- 调用工具。
- 执行 WRITE 操作。
- 自动写入或应用长期记忆。
- 展示“计划已经准备好”的完整审批卡片。

只有用户点击“继续执行”或“展开详细攻略”后，Runtime 才能进入完整计划或执行流程。LLM 只能返回意图和内容，不能直接写入 Agent 状态。

## 7. 流式与响应体验

### 7.1 立即反馈

用户发送后前端应立即追加用户消息，并显示一个轻量状态：

```text
已收到，正在理解你的请求…
```

该状态不应等待完整的 `handle_message` 返回。

### 7.2 第一响应优先

- 路由结果限制输出长度，优先返回 3～5 条内容。
- 目标和长期任务先返回方案预览，不先生成完整计划。
- 普通问题直接通过 SSE 流式显示回答。
- 完整计划、工具调用和执行过程在用户确认后开始。
- “取消任务”在处理期间始终保持可见。

### 7.3 API 与运行时方向

消息接口应尽快返回交互已接收的信息，路由和后续输出通过现有 SSE 轨迹事件推送。可以在现有 FastAPI 单进程内使用受 Runtime 管理的后台任务，不引入 Celery、Redis 或新服务；任务状态、Checkpoint 和事件仍然写入 SQLite。

建议增加或复用以下事实事件：

- `interaction.classified`
- `interaction.previewed`
- `interaction.direction_selected`
- `interaction.revised`
- `model.response.delta`

事件中记录模式、置信度、用户选择和关联交互 ID，便于轨迹页解释“系统为什么直接回答或进入计划”。

## 8. 具体示例

### 8.1 目标/长期任务

用户：

```text
给我一个学习 Python 脚本的计划
```

第一响应：

```text
建议分为环境搭建、基础语法、文件处理、网络请求和项目打包五个阶段，预计 4～6 周。第一周先完成环境配置，并写出一个可运行的小脚本。

[继续执行] [修改学习周期]
```

点击“继续执行”后，才生成详细计划和执行步骤。

### 8.2 攻略类

用户：

```text
给我一份桂林两日游攻略
```

第一响应先给出行程骨架、预算范围和一个重要避坑提醒，并提供：

```text
[展开详细攻略] [调整预算/节奏]
```

不需要先创建完整执行计划。

### 8.3 普通问题

用户：

```text
Python 的列表和元组有什么区别？
```

直接流式回答，回答结束后可提供“转为 Python 学习目标”，但不显示计划审批卡片。

### 8.4 信息不足

用户：

```text
帮我把这个做好
```

系统应先说明当前缺少对象和期望结果，并给出一个简短选择：

```text
你希望我处理的是代码、文档还是旅行计划？如果你暂时不确定，我也可以先根据你接下来提供的内容给出第一版建议。
```

## 9. 实施顺序

1. 扩展现有澄清调用为结构化意图路由，增加模式和预览测试。
2. 实现 `goal`、`guide`、`long_term` 的简短预览和按钮选择。
3. 增加 `direct` 直接回答路径，确保不进入计划和审批。
4. 增加 `AWAITING_DIRECTION` 或等价的预览等待状态。
5. 将用户选择接入现有计划生成、审批、SSE 和轨迹事件。
6. 将消息提交与完整执行解耦，确保第一响应不依赖完整执行结束。
7. 增加确定性评测：普通问答、攻略预览、长期目标预览、修改后重试、低置信度澄清、取消流式响应。

## 10. 验收标准

- 普通问题不会生成计划、审批卡片或消耗 ReAct 预算。
- 目标/攻略/长期请求在完整计划前先显示简短可用结果。
- 用户可以点击继续或修改，不需要输入“继续”才能推动流程。
- 用户未确认前不会调用工具或执行副作用操作。
- 第一响应通过流式事件逐步出现，不需要等待完整 `handle_message` 返回。
- 取消按钮在模型响应和执行期间可见且有效。
- 低置信度请求不会被静默归入长期执行流程。
- 所有路由、预览、选择和后续执行均有可审计轨迹。
- 不引入 RAG、多 Agent、MCP、Shell、Redis、Celery、微服务或工具并行。

## 11. 结论

推荐采用“复用现有澄清调用的轻量 LLM 路由 + Runtime 代码硬约束 + 简短预览 + 用户选择 + SSE 流式反馈”的方案。

这能把当前的“先完整执行、最后才反馈”改成“先给有用结果、再由用户决定是否深入”，同时保留现有 Agent 的计划、审批、轨迹、Checkpoint 和安全边界。
