# 专家用户入口全流程诊断

用户截图任务：制定一个7天的骑车计划。

## 根因

1. `POST /api/threads/{id}/expert-runs` 与内部 `ExpertAdvisoryService` 共用审计合同，没有区分用户交付任务与内部校验任务。
2. `_expert_objective` 将目标包装成“仅作为检查对象”；planner 只允许核算，researcher 只允许查来源，critic 只找问题。没有计划草稿时，所有角色都报告资料缺失。
3. 协调器仅被要求写一段综合结论并为每项数字附 source_ref，没有承担最终计划交付责任。
4. UI 将内部子任务 objective 原样显示，并用普通 `<p>` 渲染 Markdown；SUCCEEDED 被写成“已完成”，易被理解为用户任务已经完成。

## 修复

- 用户直接专家入口和普通会话的专家交接显式标记 `task_mode=user_task`。
- 用户任务角色合同允许产出可用计划，缺少非关键资料时使用明确保守假设；不再要求不存在的内部来源标识。
- 用户任务协调器交付完整 Markdown 答案；仅覆盖请求范围，并核对时长与假设一致性。内部资料审查保留原有严格来源合同。
- 基础未知的骑行计划采用明确、保守的默认边界；不默认高强度或附加下周进阶。此为产品默认假设，不是已验证的个人运动处方。
- 专家卡片使用现有 MarkdownMessage，显示用户目标而不是内部角色指令；执行状态显示“已返回 / 专家结果已生成”，避免将调用完成视为业务效果证明。

## 真实全链路验证

测试从 FastAPI HTTP 用户入口开始，经过数据库任务、实际专家 worker、真实模型、协调汇总、线程消息写入，再通过任务/产物 API 读取结果。使用隔离 PostgreSQL，不向用户现有线程写入测试数据。
