# 指代补全开发与真实验收

## 结论

已接入普通对话的长期记忆检索：明确问题直接检索；明确单实体指代由规则补全；复杂指代按需调用 LLM；不确定或调用失败则请求澄清。用户原问题保留，RRF k=60、向量/关键词各 50 保持不变。

新留出集验证了按需 LLM 的额外收益，代码默认已从初期 rules 改为 **hybrid（规则优先＋按需 LLM）**。可用 `MEMORY_REFERENCE_MODE=rules` 回退到仅规则，或 `off` 关闭。现有应用进程没有重启，不能宣称已经部署生效。

## 真实评测结果

最终使用 memory-reference-v2：312 条构造记忆，120 题（60 dev、60 holdout），新增服务实体 SVC401—SVC440，dev/holdout 实体不交叉。每类 20 题：单实体、有序指代、话题切换、当前问题自带实体、真正歧义、假设及提示词注入干扰。不是生产用户日志。

| 新留出集方案 | 有答案题严格正确 /50 | 真歧义正确澄清 /10 | 有答案却澄清 /50 | 错误实体补全 |
| --- | --- | --- | --- | --- |
| 不补全 | 14/50（28%） | 0/10 | 0 | 0（没有补全操作） |
| 仅规则 | 39/50（78%） | 10/10 | 10 | 0 |
| 规则＋按需 LLM | **48/50（96%）** | **10/10** | **1** | **0** |

这里 96% 的分母是 50 道有答案题，另 10 道澄清题单列，不能写成全部 60 题回答正确率。混合方案相比规则逐题多答对 9 题、无退化；问题自带实体的 10 题三组均正确。规则相比不补全有 26 题改善、1 题退化（原方案偶然召回并答对有序指代，规则选择澄清）。全部实际注入 ID 的 owner/project/status 校验均无违规。

开发集有答案题分别为 13/50、39/50、49/50。最终一轮实现/提示词未依据 dev 或 holdout 结果继续调参；原始结果和哈希保留。

收益集中在指代场景，测试中此类问题占比高且实体标识明确，不能把 96% 当作生产总体正确率。场景模板重复，不能把 120 题当作完全独立的 120 个业务场景。gold 已自动校验来源和分割，但尚未经过独立第二人复核。

## 剩余失败

- `v2_ref14_1`：指代模型到达 2 秒 deadline，混合组按设计请求澄清，没有猜测“后者”。
- `v2_ref15_5`：规则正确选择 SVC431，必要证据也已注入，但最终回答模型受历史中的干扰影响，引用另一个服务 SVC432，答出错误值。这个问题发生在回答环节，不能归为“指代补错实体”，也不能声称所有提示词注入风险已解决。rules 和 hybrid 都在该题失败。

另一次超时 `v2_ref13_4` 本来就应澄清，因此没有造成额外答案损失。两次超时均保留在日志和时延统计中，没有被删除或重试成成功样本。

## 调用与延迟

最终成功验收批次：

- 真实 DeepSeek 回答 **299/299 成功**，输入 93,606、输出 4,531，总计 98,137 tokens。
- 指代判断 **30 次触发，28 次成功、2 次超时取消**。相对于 hybrid 的 120 题，触发率 **25%**；其余不增加指代模型调用。
- 指代判断耗时含失败样本：P50 **1,621.83 ms**、P95 **2,005.49 ms**。2 秒是取消截止时间，取消清理产生少量超出。
- 成功指代响应计量：未缓存输入 7,915、缓存输入 3,584、输出 647，总计已知 12,146 tokens；超时部分可能有未返回 usage，不等于零计费。
- 新 embedding **121/121 成功**：40 条新记忆、81 个唯一查询，2,295 tokens；复用测试模板库的已有向量。P50 395.11 ms、P95 1,238.90 ms。实验超时为 5 秒，应用默认 embedding 超时未改。
- 回答调用 P50：off 775.88 ms、rules 768.57 ms、hybrid 776.42 ms。这不包含指代判断，不能据此宣称混合策略没有额外延迟。

RRF、预算和检索参数一致；重复 query 共享同一个真实向量。回答环节为独立评测提示词，不是全功能 Agent 运行。指代判断调用的是生产 ModelGateway，温度 0、关闭 thinking、JSON 输出、256 输出上限，单次尝试。

另有 3 次面向旧 dev 的协议诊断请求：一次供应商 HTTP 400、一次超时回退、一次正确澄清；不是最终效果样本。失败、未完成及超时请求的账单不作零费用推断。最终汇总以 [analysis.json](../../outputs/memory-reference-v2-pg-live-01/analysis.json) 为准，各批日志保留在 outputs。

## 代码及验收边界

- 新增 `memory_reference.py`：规则、中文提示词、候选白名单、有效来源校验、2 秒截止和澄清回退。
- `conversation.py`：检索前接入；在现有 job 租约事务中保存解析事件；同轮重试复用；通过现有 AskRequest 提问，提交答案后携带原问题继续检索。
- `memory_v2.py`：pin binding 加入可选 reference_binding_hash；原有调用未提供时保持旧绑定形状。
- `model_gateway.py` / `model_control.py`：可选 single_attempt；禁用指代调用的重试与 fallback，取消时清理路由调用状态。普通模型调用原有策略保留。
- `config.py`：Windows 正常启动加载模式和历史轮数配置，环境变量优先级保持不变。

初版识别 SVC 标识、PROJ- 标识和带引号的明确服务/项目名称。不是通用 NER，也没有接入项目目录别名。只使用当前线程最近 3 个完整成功轮次；不使用召回记忆反推实体。跨 owner、来源变更、快照篡改拒绝复用。

最终评测完成后增加 reference-v4 的类型边界：明确询问项目时不把 SVC 标识当项目，询问服务时不把 PROJ 标识当服务。该改动不是根据留出错误调参；新增边界测试，并逐条比较全部 120 题的规则结果和 LLM 输入，完全不变。评测时源码保存在 `frozen-memory_reference.py`，改动与默认 hybrid 激活记录见 [post_eval_validation.json](../../outputs/memory-reference-v2-pg-live-01/post_eval_validation.json)。原始运行哈希不重写。

Agent run 阶段的 interactions 查询未套用对话消解；它没有相同完整对话输入契约。本次覆盖普通对话调用链，未宣称已覆盖所有 Agent 阶段。进程若在模型返回后、持久化前崩溃，可能重做解析；保证的是持久化后的重试复用，不宣称模型调用 exactly-once。

## 测试

主回归 163 项通过；增加来源内容变更、pin 来源绑定、服务/项目类型边界和数据集校验后，专项 21 项通过。实际 worker 测试覆盖原问题保留、补全检索、澄清、回答澄清后的继续执行和同轮重试。

扩大检查时 3 个旧路由测试失败：一个计费模式预期与当前 observe 默认不符，另两个测试在创建“输出额度超过工作窗口”的模型配置时提前被拒绝。测试进程中移除本次路由改动后仍全部复现，未修改这些无关业务规则。

最终默认模式回归曾读到正在被其他工作修改的 `model_admin.py` 的临时语法错误；该文件未被本任务修改。随后重新运行 64 项对话及指代回归：59 通过、5 项启动相关失败，原因均为 `ModelAdminService.ensure_profile()` 不再接受启动入口仍在传入的 `capabilities_env` 参数。该接口变更在本轮最初 163 项回归通过之后发生。本任务没有覆盖这部分并行修改；当前整个工作树不能声明整体验收全绿。指代和网关专项 21 项在最新默认配置下通过。
