- **部署变更**：成本最低、最易排除，且能一次性排除代码引入

- **命中即收敛**：任一步出现异常证据，立即围绕该异常深挖，不再往下走
- **无异常则继续**：前一步排除干净才进入下一步

这样“固定顺序”只是默认起点，不是必须走完的清单。

### 2. 适用范围要写死边界
“仅数据库超时排查”这个限定很关键，但当前流程里混入了非 DB 因素（下游阻塞、配置变更、流量突增）。建议拆成两层：

- **主流程（DB 超时）**：部署变更 → 慢查询 → 连接池
- **连接池耗尽后的分支**：连接泄漏 / 下游阻塞 / 流量突增 / 配置变更

否则“仅数据库超时”和“下游阻塞导致池满”会自相矛盾——池满的根因可能根本不在 DB。

## 每步的证据与最小验证动作（建议固化）

| 步骤 | 观察证据 | 最小验证动作 | 命中后 |
|---|---|---|---|
| 部署变更 | 版本号、配置变更记录、变更时间 vs 故障时间 | 比对变更窗口与错误起始点 | 围绕该变更验证，回滚需人工决策 |
| 慢查询 | 慢查询日志、DB 会话状态、SQL 耗时分布 | 查 processlist / 慢日志 | 定位具体 SQL 与执行计划 |
| 连接池 | active/pending 曲线、连接持有时间、获取等待时长 | 拉时间序列 + 线程栈 | 进入池满分支 |

## 退出条件（建议明确）
- **确认原因**：定位到具体根因并有证据闭环 → 退出，交人工处置
- **问题无关**：证据显示与 DB 超时无关（如纯网络、纯上游）→ 退出，转对应域
- **证据不足**：无法在只读范围内收敛 → 退出，升级人工，不猜测

## 两个必须保留的约束
- **只读**：全程不写、不改配置、不重启
- **不自动重启**：即使确认池满，重启只是掩盖，且会丢失现场

## 一句话总结
流程可复用，但要把“固定顺序”改成“默认顺序 + 命中即收敛”，把“仅 DB 超时”和“池满分支”的边界划清，并固化每步的证据、最小验证动作和退出条件。
